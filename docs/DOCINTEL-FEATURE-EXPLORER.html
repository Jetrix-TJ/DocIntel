The pipeline, stage by stage

// one document, start to finish

Follow a single document from .process() to a delivered record. build_pipeline() wires all eleven stages from one call — you never hand-assemble the sequence.

1 · intake

A plain call, no queue required — pipeline.process(document_id, source_path). Your own inbox rule or upload handler decides when this fires.

2 · filter

An .eml/.msg is unwrapped into one item per real attachment; .docx/.xlsx converts to PDF first. Non-document attachments drop before anything expensive runs.

3 · classify

Claim rules (markers + vetoes) decide whose document this is; a doc_type ladder — ordered rungs, first match wins — decides what kind it is.

4 · persona

(sender_fingerprint, doc_type) resolves to a persona — a hit, or a hard_miss that escalates rather than guessing.

4b · profile

Resolves the persona's processing_profile — which export layouts and reconciliation behavior apply automatically.

5a · cached rules

The persona's saved selectors run — zero AI calls. The high-volume path for any company already onboarded.

5b · vision

Gemini answers only the specific fields a persona's field_hints name — never classification, never document structure.

5c · escalate

A genuine hard miss becomes a real, persistent review-queue job — never a silent drop.

6 · capture

Adjust ops run: alias resolution, sign normalization, derived-value computation — from the closed op registry.

7 · gate

Decides lane/review_flag/regen_flag. Any beforeEmit hook fires right after, seeing the real decision.

8 · emit

Always exactly one record — even a dead-lettered document. count(intaken) == count(emitted) is machine-checked, not a convention.

Why this order matters. Classification and persona lookup happen BEFORE any AI call — a company with no configuration yet is caught cheaply at Stage 4, not after an expensive vision round-trip. The confidence gate runs AFTER extraction finishes, so a real-time notification hook always sees the finished routing decision, never a partial one.

What one result looks like

// real output, not a mock-up

This is a real output record — actually run through docintel process against a real invoice in this project's test corpus (trimmed to the fields that tell the story; the full record also carries every line item, the confidence of every other field, and a full audit trail):

{
  "schema_version": "1",
  "document_id": "northstar-edco-077087",
  "doc_type": "standard_invoice",
  "disposition": "processed",
  "lane": "high",
  "review_flag": false,
  "fields": {
    "vendor_name": "EDCO WASTE & RECYCLING SERVICE",
    "prior_balance": "298.34",
    "current_charges": "69.62",
    "total_printed": "367.96"
  },
  "derived": {
    "amount_payable": "69.62",
    "payable_basis": "current_charges",
    "carried_balance": "298.34"
  },
  "confidence": {
    "total_printed": 0.90,
    "current_charges": 0.99
  }
}

The printed total is 367.96 — the biggest number on the page, in the biggest box. The amount actually owed is 69.62: a prior balance of 298.34 was already carried forward (derived.carried_balance), and only the current period's charges are due — this exact invoice's filename is literally "current charges can be misleading, paying $69.62." derived.amount_payable is never the raw printed total by default — it's computed from prior_balance and current_charges, the two fields actually printed on the bill. fields is always what's printed, verbatim; derived is always the answer to "what do we actually pay" — keeping the two separate is the one distinction this whole system exists to protect.

Gemini vision extraction

// the fallback, and its boundary

Stage 5b calls Gemini only for fields a persona's own field_hints name — it is never given free rein to decide what a document contains or how it should classify. Sanitizing whatever it returns (adapters/vision/policy.py) is a dedicated boundary, not a trust assumption.

fake

Returns nothing — wiring checks, no API key, no network call.

cassette default

Replays recorded responses offline — deterministic, reproducible, no billing.

record

Calls Gemini once and writes the response into a cassette fixture — how new fixtures get made.

live

Actually calls Gemini. Different answer every run, costs money — used deliberately, never as a silent default.

The boundary that matters: classification, routing, and lane decisions are made entirely outside the vision call. A field registered as money/currency that comes back the wrong Python type raises loudly at score time rather than silently comparing wrong.

One pack.json, a personas/ folder, zero Python. Gets the ladder, claim guard, field sets, aliases. Right when a company's logic is fully covered by the shared op registry.

Hybrid

A thin class wrapping a DataPack, adding exactly one hook for a non-printed fact (e.g. SPT Metals' weight-tier margins). ~120 lines, not ~1,200.

Full module

A bespoke Python package (~1,150–1,290 lines): fingerprint resolution, billing-convention tables, reference collection. Right when a company needs several bespoke hooks.

A fifth vantage point, not a fifth shape: the same pure-data pattern authored entirely outside this repo — see "Onboarding — no repo access" in Compose above.

Writing classification — pack.json

// which company, which document type

A pack claims a document when any rule holds and no veto holds, then an ordered ladder of rungs — first whose condition holds wins — decides the doc_type. Both are plain JSON; nothing here is Python.

The company-level fields — every key at the top of pack.json:

name

The pack's own slug — matches its folder name. Shows up in telemetry and CLI output when a document routes through it.

default_currency

The fallback when infer_currency's whole ladder (ISO code → symbol → tax regime → vendor address) comes up empty. Applied last, flagged currency_inferred_weak when it fires.

doc_types

Every document type this vendor can send — ["standard_invoice", "credit_memo"]. Each name needs a matching key under fields and, usually, a ladder rung that can reach it.

thresholds

Per-field confidence floor for the "high" (auto-approved) lane — {"total_printed": 0.90}. A field scoring below its threshold routes to human review even if nothing else flagged it.

Which fields exist — the fields block, one entry per doc_type:

all

Every field this doc_type can carry, extracted or not. The complete vocabulary a persona's field keys are checked against (validation rule V1).

required

Must be covered — by a selector, or by an op that supplies it — or the persona write is rejected outright unless its status is "draft" (V13).

any_of

At least one field from this group must be present. For a vendor that prints either a PO number or a contract number, never guaranteed to print both.

derived_only

Computed by an adjust op, never printed as a standalone value a selector could point at — amount_payable is the standing example. A selector naming one of these is rejected (V10).

{
  "name": "acme_widgets", "default_currency": "USD",
  "doc_types": ["standard_invoice"],
  "thresholds": { "total_printed": 0.90 },
  "fields": {
    "standard_invoice": {
      "all":          ["vendor_name", "invoice_number", "total_printed", "prior_balance", "current_charges", "amount_payable"],
      "required":      ["vendor_name", "invoice_number", "total_printed"],
      "any_of":        [],
      "derived_only":  ["amount_payable"]
    }
  }
}
markers

A name/address specific enough that no other business prints it — the primary guard for an AP department claiming by bill-to.

corroborated_markers

A weak marker (a bare ZIP) that only counts alongside a second co-occurring token — avoids over-claiming on the weak marker alone.

alias_table

Claims by sender, reading the pack's own vendor alias table — compiled once at load, so it's the shipped table only. DOCINTEL_EXTRA_PERSONAS_DIR's overlay does NOT reach this (tested) — a brand-new carrier needs a real table edit to be claimed, not just an overlay file.

roster_on_short_line

A client name, but only on a short line (a bill-to block) — not a line-item description that happens to mention the client.

Vetoes exist because a marker can be present for the wrong reason: every_marker_hit_in_block refuses the claim if every marker hit sits inside a SHIP TO block — a delivery address says where goods went, not who owes the money.

"claim": {
  "rules": [
    { "kind": "markers", "scope": "primary", "values": ["ACME WIDGETS", "ap@acmewidgets.example"] }
  ],
  "vetoes": [
    { "kind": "every_marker_hit_in_block", "anchor": "\\bship\\s*to\\b" }
  ]
},
"ladder": {
  "default": "invoice",
  "rungs": [{
    "name": "credit_memo_title", "doc_type": "credit_memo",
    "when": { "all_of": [
      { "signal": "title_near_top", "params": {"pattern": "credit memo", "max_words": 7, "max_line_index": 10} },
      { "not": { "signal": "money_table_present" } }
    ]}
  }]
}

All 12 signals a rung's when can name (composed with all_of / any_of / not):

SignalParamsAsks
pattern_in_scopepattern, scopeDoes this regex appear anywhere in scope's text?
short_label_linepattern, max_wordsOn a line no longer than max_words? (a banner, not buried prose)
title_near_toppattern, max_words, max_line_indexA genuine title: short AND near the top of page 1?
text_near_toppattern, max_line_indexNear the top, no length limit — a letterhead block.
label_with_corroborating_valuelabel, same_line/next_line predicateIs a label match backed by a real value near it?
all_matches_negativepattern, scopeMatches at least once, and every match is negative?
role_shapeprimary_exactly, supporting_at_leastDoes the page-role shape match (e.g. 1 primary + ≥1 supporting)?
shared_pagination_footer—Does every page share one "N of M" footer sequence?
money_table_presentmin_money_tokensUsed as a NEGATIVE: a titled "statement" with a charges table is still a bill.
text_source_isvalue ("native"/"ocr")PDF text layer or OCR? A trust signal, not a content fact.
noise_ratio_abovethreshold, role, ocr_onlyDoes a page read as handwriting rather than print?
distinct_printed_aliases_at_leastcount, scopeDoes the alias table match ≥ count distinct printed names?
Fail-loud, at load time. An unknown signal name, region, or misspelled param raises the moment the pack loads — never a rung that silently never fires.

Writing extraction — persona.json

// where each field sits, and what shape it is

One persona per vendor: rule_version, status, doc_type, sender_fingerprint, and a field_selectors list mixing three selector shapes.

{
  "rule_version": "v1", "status": "draft",
  "doc_type": "invoice", "sender_fingerprint": "acme_widgets|acme_widgets",
  "field_selectors": [
    { "field": "vendor_name", "region": "top-left", "pattern": "text" },
    { "field": "bill_to_name", "anchor": "BILL TO", "region": "near-anchor", "pattern": "text" },
    { "field": "total_printed", "anchor": "TOTAL", "region": "near-anchor", "pattern": "currency",
      "adjust": ["derive_amount_payable"] }
  ]
}

KeyRequiredMeaning

anchor_occurrenceno · default firstfirst/last (ordinal) or mid_line (positional — withheld on OCR).

captureno · default firstfirst stops at the first match; all_matches collects every one.

Never target amount_payable directly. It's computed by an adjust op from prior_balance + current_charges + total_printed — a selector naming it is rejected outright (validation rule V10). On 7 of the original 10 corpus documents, reading the printed total straight onto it would look perfectly correct and still be wrong.

The other two selector shapes. field_selectors mixes all three freely — a persona is usually mostly field_selector entries, one row_group_selector for the line-items table, and at most one scanline_selector.

{ "row_group": "line_items", "table_anchor": "DESCRIPTION",
  "column_headers": { "description": "DESCRIPTION", "charges": "CHARGES" },
  "columns":        { "description": "text",         "charges": "currency" },
  "sub_group": { "anchor": "WORK ORDER#:", "field": "work_order", "pattern": "text" },
  "row_count": { "min": 1, "max": 40 }, "allow_empty_cells": true }
KeyRequiredMeaning
row_groupyesA name for this repeating group — becomes record["line_items"] on the emitted record.
table_anchoryesHeader row text used to find the table on the page.
regionnoNarrows the page search before looking for table_anchor.
columnsyesColumn name → pattern. Matched by the printed header text, never by position — a reordered column doesn't silently break it.

{ "scanline": true, "region": "remittance-block",
  "asserts": [
    { "field": "total_printed",  "as": "digits_no_decimal" },
    { "field": "account_number", "as": "digits_only" }
  ] }

A scanline_selector reads the OCR-A digit line printed along a remittance stub's edge. It produces no field value — it can only raise or lower confidence on fields a field_selector already extracted. asserts[].field may only name total_printed, account_number, invoice_number, or due_date — never amount_payable or current_charges (V7).

Boosts (a cross-check agreeing) are capped: the product of every boost on one field may never exceed 1.10, and a boost can never lift a field above 0.99.

The 14 validation rules (V1–V14) — run at persona-write time, any single failure rejects the WHOLE write:

V1Every field is in the pack's registered field set for that doc_type.
V2Every adjust op is registered (base + pack).
V3Every region is in the closed enum.
V4Every pattern is a named pattern or passes the restricted-regex rules.
V5A selector with a non-unique anchor and no region is rejected.
V6A bare-digit regex needs a narrowing region or column_headers.
V7scanline_selector.asserts[].field is within the permitted set.
V8sub_group nesting depth ≤ 1.
V9row_count is a range, never an equality.
V10No selector produces a field the pack marks derived_only — the F1 footgun guard.
V11Total serialized persona size ≤ 64 KB.
V12few_shot_examples ≤ 3 entries, none from a flattened_annotations document.
V13Every required field is covered — by a selector, an op, or the persona is draft-only.
V14A pattern capturing only fixed text needs an anchor/region — no anchor may restate a captured value.

Run explicitly with docintel validate-persona <persona.json> --pack-file <pack.json> — it does not run automatically at docintel process startup.

Troubleshooting — real gotchas we actually hit

// found while building this against real invoices

A field grabbed the wrong text

region: "near-anchor" is a wide box (300pt right, 40pt below the anchor) — a label at the same height in a neighboring column can leak in. The "text" pattern makes this worse: it accepts whatever candidate it sees FIRST.

Fix: use a targeted regex instead of the generic shortcuts. For a party name, an ANCHORED Title Case shape (^([A-Z][a-z]{1,15}\.?(?: [A-Z][a-z]{1,15}\.?)?...)$) rejects an all-caps label like INVOICE NO. outright, letting the pattern loop fall through to the real value on the next line.

A date field came back empty

The named "date" pattern only parses month-first strings (Aug 19, 2026). A day-first date (19 Aug 2026) silently fails — the field is missing, not wrong.

Fix: a plain regex instead — ([0-9]{1,2}\s{1,3}[A-Za-z]{3,9}\s{1,3}[0-9]{4}) — records the raw printed text rather than failing to normalize it.

A brand-new carrier isn't claimed, even with a correct persona in the overlay

digitaldirection claims via alias_table, compiled once at import from the shipped table — DOCINTEL_EXTRA_PERSONAS_DIR's overlay reaches persona lookup and fingerprinting but never that claim decision.

Fix: either the carrier already bills an existing MANAGED_CLIENTS client (the secondary claim rule), or add it to the real LITERAL_ALIASES table — a genuine code change. northstar doesn't have this gap: it claims by its own fixed identity, never the vendor's name. Check a pack's claim rule kind before assuming the overlay alone is enough.

Everything lands in the review lane

Normal for a brand-new persona — "status": "draft" applies an automatic confidence penalty on every document. Promote to "active" once you've checked real coverage.

How to read this

  • One front door: build_pipeline(vision=…) returns a Runner. Pick a Vision mode, whether you're loading Packs of your own, and whether a Jobs queue should persist review-worthy documents — then layer in optional features.
  • The two extension points compose independently: DOCINTEL_EXTRA_PERSONAS_DIR adds a vendor to an existing pack (e.g., one of the reference examples); extra_packs= adds a whole new company. Neither ever touches the installed package, so pip install --upgrade can't wipe them.
  • Vision only ever answers questions a persona already poses — it never decides classification or invents document structure. fake is for wiring checks, cassette replays recorded responses offline (the default, reproducible), live actually calls Gemini.
  • The "always on" row is not optional — it's the point. Emit-always, the 14-rule validator, the draft confidence penalty, the safe unclaimed-vendor path, and in-run dedup all run automatically. You don't wire correctness guarantees — the pipeline provides them.
  • Operational tasks live in the CLI, not your code. Draining the review queue, exporting a spreadsheet, reconciling against contracts, checking queue health — see Command-line operations above.

Generated for sharing — a single self-contained HTML file, no build step. Every toggle's generated code, every table, and every gotcha above reflects a real, verified docintel API surface — install to onboarding to gold-data scoring, all in this one page.
