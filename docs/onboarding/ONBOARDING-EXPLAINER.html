docintel · Vendor Onboarding

Fill in one file. Get one reviewed draft. Nothing goes live without a human.

This is the open, documented space to add a new company's document types and fields — the thing raised at standup: "we need a certain area where the particular team can add their own modules." One template you fill in without touching any code, one optional automated first draft, and one review step that never gets skipped.

The whole flow, in three steps

  1. You fill in a template

    Company name, how to recognise its documents, every document type it sends, and the fields your team actually needs per type — plus one real sample document per type. No engineering background required; this is the entire interface.

  2. A reviewer gets a first draft increasingly, automated

    One command sends your sample document to Claude once and gets back a plain-language field list — never a final answer, always a starting point for step 3.

  3. A human reviews it always, no exceptions

    Checked against the real sample, corrected where needed, tested, and only then does this company's documents start routing automatically.

Step 1 — the template

docs/onboarding/COMPANY-CONFIG-TEMPLATE.md is the form. It asks for exactly what a reviewer needs and nothing else:

SectionWhat you fill in
CompanyName, and every printed identifier that marks a document as theirs
Document typesEvery distinct kind they send — invoice, credit memo, statement — each with a real sample attached
FieldsPer document type: what your team needs, where it sits on the page, and — critically — whether it's computed rather than just printed
Billing conventionsNet vs. gross balances, if it's a recurring bill — "not sure" is a completely fine answer here

A document type with no sample attached can't move to step 2 — everything downstream is built from looking at a real page, not from description alone.

Step 2 — the automated first draft

Writing a field list by hand, from nothing, for every new company doesn't scale. That was the exact gap raised at standup:

Standup, Aug 18

"The schema generation, or the classification generation, or the persona generation — you are proposing it to do it by human. I think we also need to find a way… we can try to do it with some agents."

— Anamul

One command runs the draft:

docintel generate-persona path/to/a/sample.pdf --company "Acme Corp"

It sends that one document to Claude once and asks for a plain-language description of every field it recognises — never the value itself, never invented field names, only names from this project's own fixed vocabulary of fields it already knows how to score: 

{
  "status": "draft - not reviewed, do not use in production",
  "company_name": "Acme Corp",
  "spec": {
    "fields": [
      {
        "name": "total_printed",
        "type": "currency",
        "hint": "bottom right of the page, beside 'Total Amount Due'"
      }
    ],
    "row_groups": [],
    "notes": "..."
  }
}

What it deliberately will not do

It never generates the pixel-level selector geometry a real persona eventually needs. An earlier internal test found that's the one part that does not generalize from a single blind pass — the field list and one-sentence hints did generalize, the coordinates didn't. So the draft gives a reviewer exactly the part worth having early, and leaves geometry to a human, informed by this draft rather than starting from a blank page.

Step 3 — human review, always

Standup, Aug 18

"Let's say the generation was done and the quality is not good — then we will mark it down that okay the quality is not good, and human review it. We only approve it."

— Anamul, agreed by JA

A reviewer:

  • Reads the draft next to the same sample document and confirms each field and hint is right — not close, right.
  • For a genuinely new company, starts from a real scaffold instead of reading an existing pack's source by hand: docintel new-pack <slug> --company "..." --doc-type ... --hints <draft> writes a starting pack.json and persona — every selector geometry field an explicit placeholder, nothing registered anywhere.
  • Self-checks it before asking anyone else to look: docintel validate-persona <persona> --pack-file <pack.json> runs the same rules the real pipeline enforces on every shipped persona, and names the first thing wrong.
  • Builds or corrects the real persona: the selector geometry and claim rules the draft never attempts.
  • Tests it against the sample document(s) and confirms the extracted values before anything goes live.

Every generated draft is labelled "status": "draft - not reviewed, do not use in production" on disk, and nothing on the real extraction pipeline's path reads it. draft already carries a real, tested consequence elsewhere in this system — an automatic confidence penalty that routes to review rather than auto-approving — so this reuses that guarantee instead of asking anyone to trust a new promise.
