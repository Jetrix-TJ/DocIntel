Overview — what this is, and how it works

DocIntel is a library you install into your own project — a fresh install knows about zero companies, zero document layouts. For each vendor, you can write two small JSON files describing what its documents look like: pack.json (whose document this is, and what type) and persona.json (exactly where each field sits on that specific layout). Once a vendor's persona exists and validates, every future document matching that layout — any file format, native or scanned PDF, image, DOCX, XLSX, or an email attachment — extracts through pure deterministic logic: anchor found, region checked, pattern matched.

A persona has to be written and covers only the one vendor layout it was built for. Any document from a vendor with no persona yet — the common case until you've onboarded it — falls straight to the Gemini vision (LLM) layer instead, automatically. That's why, in practice, most of today's bulk extraction volume runs through the LLM path: persona coverage is still small relative to the number of distinct vendor layouts in real traffic. The deterministic path only takes over for a vendor once its persona exists — from that point on, every document from that vendor extracts for free, with zero AI involvement, permanently.

Writing personas for your highest-volume vendors is what shifts bulk extraction off the LLM path and onto the free deterministic one — each new persona removes that vendor's entire future volume from the AI cost line. The two file-format questions are independent of this: every format is supported on both paths — a scanned TIFF with a persona extracts deterministically; a native PDF with no persona still goes to vision. Format never decides which path runs; whether a matching persona exists does.

What's available — the full feature list

Core extraction

Deterministic rule-based extraction, validated against a closed 14-rule grammar. Gemini vision fallback for scalar fields and repeating tables. Auditable, multiplicative confidence scoring. A business-logic derivation layer kept separate from raw extraction.

Format support

PDF (native and scanned), PNG/JPG/BMP/GIF/TIFF, DOCX, XLSX (with a LibreOffice-free fallback), TXT/CSV/HTML, and .eml/.msg with per-attachment processing — one call handles all of them.

Classification

A 12-signal, priority-ordered ladder per company, plus claim rules with 4 different matching strategies for how a document gets attributed to your organization at all.

Operational

Opt-in library telemetry, a real human-review job queue with cron-friendly status checks, and a local web UI to work that queue by hand.

Evaluation

A hand-labelled gold corpus + scoring engine, isolated evals per stage, and a regression-only comparison gate — CI doesn't require 100%, only that nothing which used to pass now fails.

Extensibility

Add a vendor, or a whole new company, with zero repo access. 8 named hook sockets for custom behavior at any pipeline boundary, without forking the codebase.

The mental model — 60 seconds

Four things happen to every document, in this order. Everything else in this guide is detail on one of these four.

1. Whose is it, what is it

pack.json decides. A claim rule says "this document belongs to us"; a ladder decides which document type it is. Data only — no code.

2. Where's each field

If you've written a persona.json for this exact sender + doc type, its selectors run — zero AI calls, deterministic, free.

3. No rules? Ask Gemini

Only reached when there's no persona at all, or the persona's read came back weak. A fallback, not the primary path.

4. Score it, route it

Every field gets a confidence score. Clears the bar → done automatically. Doesn't → a human sees it, never silently guessed.

The one sentence that explains most first-time confusion: the library extracts nothing by default. A fresh install has zero pre-loaded companies — pack.json + persona.json are things you write, for your vendors. Nothing "just works" out of the box because there's nothing configured yet to work.

1

Write your first pack.json

// classification: whose document, what kind

One file per company. Two jobs: a claim (is this document ours?) and a ladder (what kind of document is it?). Both are plain JSON — nothing here is Python.

1a — Claim: which rule kind do you need?

Your situationUse
A document is addressed to you, from any sender — you have a specific printed name/address/email only your organization's documents carry.markers ← default choice, use this first
Your best marker is weak on its own (a bare ZIP code, a common word) and would over-claim alone.corroborated_markers — pair it with a second co-occurring token
You're claiming by who sent it, not who it's addressed to — you manage many vendors/carriers billing you under one system.alias_table — needs a maintained vendor list, compiled once at load
A client/company name is printed on a short label line (a bill-to block), not buried in paragraph text.roster_on_short_line
One tested gap worth knowing up front: alias_table compiles the vendor list once when the pack loads. If you're adding vendors without repo access (see Vendor paths below), the overlay reaches persona lookup fine but does not reach this specific claim decision — a brand-new carrier under an alias_table pack still needs a real edit to the shipped table. markers-based claims don't have this gap at all.

1b — The ladder: this is what "everything classifies as the same type" actually means

The ladder is opt-in per document type. If you never write a rung for credit_memo, nothing will ever classify as credit_memo — no matter how clearly the document says "CREDIT MEMO" across the top. This is the single most common first-config surprise: it isn't a bug, it's exactly what an empty ladder with only a default means.

pack.json{ "name": "acme_widgets", "default_currency": "USD", "doc_types": ["standard_invoice", "credit_memo"], "claim": { "rules": [ { "kind": "markers", "scope": "primary", "values": ["ACME WIDGETS", "ap@acmewidgets.example"] } ], "vetoes": [] }, "ladder": { "default": "standard_invoice", "rungs": [ { "name": "credit_memo_title", "doc_type": "credit_memo", "when": { "signal": "title_near_top", "params": { "pattern": "credit memo", "max_words": 7, "max_line_index": 10 } } } ] } }

Rungs are checked top to bottom, first match wins, then it stops. title_near_top is the workhorse signal for "does a short line near the top of page 1 say X" — it covers most doc-type distinctions on its own. The full 12-signal vocabulary (pattern matching, corroborated labels, page-role shape, OCR/noise trust signals, and more) is in Classification, further down this page — add rungs there as you discover more document types, one rung per type.

Validate structure early: a pack with a genuinely malformed claim rule or an unknown signal name fails loudly the moment it loads — never a rung that silently never fires. If docintel process raises on your pack, that's the fail-fast working as intended; fix the named field and re-run.
2

Write your first persona.json

// extraction: where each field actually sits

One persona per sender_fingerprint × doc_type. A list of field_selectors — each one says: find this label (anchor), look in this direction from it (region), expect this shape (pattern).

If you find yourself writing Python to pull one field out — stop. Every field should express as an anchor/region/pattern selector. A custom script around the library isn't a faster path, it's a parallel extraction system that never gets validated, never gets scored against gold data, and silently drifts from everything else. If a field genuinely can't be expressed in the grammar, that's worth reporting as a real gap in the region/pattern vocabulary — not a reason to route around it.

Build one field, step by step

Take a real sample document. Pick one field — say, the invoice total. Three questions, in order:

1. Anchor

What's the exact printed label next to it? Copy it verbatim — "Total Due:", not "the total label."

2. Region

Where's the value relative to that label? near-anchor covers most cases — it's the default choice.

3. Pattern

What shape is the value? currency, date, text — a named type first, a custom regex only if none fits.

personas/acme_widgets.json{ "rule_version": "v1", "status": "draft", "doc_type": "standard_invoice", "sender_fingerprint": "acmewidgets.example|acme widgets", "field_selectors": [ { "field": "vendor_name", "region": "top-left", "pattern": "text" }, { "field": "invoice_number", "anchor": "Invoice #", "region": "near-anchor", "pattern": "text" }, { "field": "total_printed", "anchor": "Total Due:", "region": "near-anchor", "pattern": "currency", "adjust": ["derive_amount_payable"] } ] }

Region — when to reach past near-anchor

SituationRegion
A labelled value, close to its own label — the common case.near-anchor
A value in the same table row as another already-found value.same-row / same-cell
No printed label at all — the value just sits in a fixed corner (a logo-adjacent vendor name).top-left / top-center / top-right
A whole address/name block under a label, spanning several lines.label-block
A total that isn't always on page 1 — some vendors print it on the last page only.totals-block — checks the last page first, then page 1
A repeating charge/line-item table.line_items / last-table-row
You know exactly which page a value is on, regardless of role.first-page / last-page / any-page / page:N
Multi-page tables — a real, current limit. A line_items table only ever reads rows on its anchor's own page. If a vendor's line-item table regularly continues onto page 2, rows past page 1 won't be captured today — there's no region trick that works around this; it's an unbuilt refinement, not a config mistake.

The one hard rule

Never target amount_payable directly. It's computed by the derive_amount_payable op from prior_balance + current_charges + total_printed — a selector naming it is rejected outright at validation. Reading the printed total straight onto it looks correct on most invoices and is silently wrong on the ones that carry a balance forward.

Self-check before you run anything

terminaldocintel validate-persona personas/acme_widgets.json --pack-file pack.json

Runs the same 14 validation rules every shipped persona is held to — the first thing wrong (an unregistered field, a non-unique anchor with no region, a placeholder left in) is reported clearly enough to fix and re-run, before you ever process a real document.

3

Run it

// wire pack + persona together, process a real document

run_pipeline.pyfrom docintel import build_pipeline from docintel.adapters.vision.fake import FakeVision from docintel.packs.datapack import load_pack_file pack = load_pack_file("pack.json") pipeline = build_pipeline(vision=FakeVision(), extra_packs=[pack]) record = pipeline.process(document_id="acme-001", source_path="sample_invoice.pdf") print(record["disposition"]) # "processed" | "skipped" | "dead_letter" print(record["lane"]) # "high" | "medium" | "review" | "low" print(record["fields"]) # raw printed values, as your selectors found them print(record["derived"]) # business-logic outputs - e.g. amount_payable

vision=FakeVision() is deliberate here — it answers nothing, so this run proves your persona's selectors alone, with zero API calls and zero cost. Once fields come back right, switch to CassetteVision (replays a recorded response, still free) or GeminiVision() (real calls, real cost) — see Vision & Gemini below.

Reading the result: fields holds exactly what your selectors captured — raw, pre-business-logic. derived holds what the adjust ops computed from those raw values. Always read derived.amount_payable for what's actually owed, never fields.total_printed directly — that's the one distinction this whole system exists to protect.

What that actually looks like — a real record, actually run through docintel process against a real invoice in this project's test corpus (trimmed to the fields that tell the story):

real output — not a mock-up{ "schema_version": "1", "document_id": "northstar-edco-077087", "doc_type": "standard_invoice", "disposition": "processed", "lane": "high", "review_flag": false, "fields": { "vendor_name": "EDCO WASTE & RECYCLING SERVICE", "prior_balance": "298.34", "current_charges": "69.62", "total_printed": "367.96" }, "derived": { "amount_payable": "69.62", "payable_basis": "current_charges", "carried_balance": "298.34" }, "confidence": { "total_printed": 0.90, "current_charges": 0.99 } }

The printed total is 367.96 — the biggest number on the page. The amount actually owed is 69.62: a prior balance of 298.34 was already carried forward, and only the current period's charges are due — this exact invoice's filename is literally "current charges can be misleading, paying $69.62." That gap between what's printed and what's owed is the whole reason derived and fields stay separate.

An .eml/.msg is unwrapped automatically — every real attachment inside becomes its own separate document. Your pack.json and persona.json never know or care which format a document arrived in — one persona works across every format a vendor happens to send in, with zero extra config.

Vision & Gemini — when it's actually used

// the fallback, not the primary path

ModeUse it for
fakeWriting and testing your persona (Step 2-3 above) — answers nothing, no key, no cost.
cassette (default)Everyday development and CI — replays a recorded response, deterministic, no billing.
recordMaking a NEW cassette fixture — calls Gemini once for real, saves the response for future replay.
liveProduction, or deliberately checking real accuracy. Costs money, different answer every run.

Gemini is only ever reached two ways: no persona exists at all for this sender+doc_type (a genuine hard miss), or your persona's cached selectors ran but collapsed — two or more fields came back weak, or most of what you declared produced nothing. A correctly written persona for a known vendor should cost zero vision calls, ever.

What Gemini actually gets asked

Four tiers, in order, whichever applies first:

  1. A caller's explicit field-list override (rare — building the pipeline by hand).
  2. Your persona's own field names — the moment you have a persona, even a currently-collapsing one, Gemini asks about exactly your fields, not a generic guess.
  3. Your pack's vision_defaults block — for a vendor you haven't written a persona for at all yet (see below).
  4. A hardcoded 4-field generic default — last resort, no pack declaration at all.
pack.json — for a vendor with no persona yet"vision_defaults": { "standard_invoice": { "fields": { "account_number": "text", "total_printed": "currency" }, "tables": { "line_items": { "date": "date", "description": "text", "amount": "currency" } } } }

Plain type names only — text/currency/decimal/date/integer — never a regex, and never read by the rule-based grammar engine, only by Gemini. This is the right tool for the "1000 unknown vendors, no persona will ever exist for most of them" case, not a substitute for writing a real persona on your highest-volume vendors.

GEMINI_API_KEY in a .env file is only needed for --vision live/record. fake and cassette — everything you'll use through Steps 1-3 — need no key at all.

For the full four-tier field/table resolution order and the vision_defaults deep dive, see the extended Vision reference below.

Gemini vision extraction

// the fallback, and its boundary

Stage 5b calls Gemini only for fields (and now, tables) a persona's own field_hints — or a pack's own vision_defaults — name. It is never given free rein to decide what a document contains or how it should classify. Sanitizing whatever it returns (adapters/vision/policy.py) is a dedicated boundary, not a trust assumption.

fake

Returns nothing — wiring checks, no API key, no network call.

cassette default

Replays recorded responses offline — deterministic, reproducible, no billing.

record

Calls Gemini once and writes the response into a cassette fixture — how new fixtures get made.

live

Actually calls Gemini. Different answer every run, costs money — used deliberately, never as a silent default.

The boundary that matters: classification, routing, and lane decisions are made entirely outside the vision call. A field registered as money/currency that comes back the wrong Python type raises loudly at score time rather than silently comparing wrong.

Line-item tables, not just scalar fields

Gemini can now also transcribe a whole repeating table — a charge/line-item breakdown — into record["line_items"], alongside the flat fields it already answered. Same security boundary as scalar fields: only a requested table name passes, only its declared columns survive per row, and a malformed row is dropped, never raised.

What to ask for is resolved in the same four-tier order, for fields and tables independently:

TierSourceWhen it applies
1Constructor override (VisionOneShot(table_requests=…))A caller building the pipeline by hand wants one fixed request for every document — highest priority.
2A known persona's own row_group selectorThe exact same selector the grammar engine (5a) already uses — no new authoring. Derived automatically the moment 5a's cached read collapses.
3The matched pack's vision_defaultsNo persona exists for this vendor at all — the 1000-unknown-vendor case. Declared once on the pack, in plain JSON.
4Hardcoded generic defaultNothing above applies — the 4-field scalar default, no tables.

vision_defaults — Gemini-only config, for a vendor with no persona

A pack's own declaration of what to ask Gemini for, when no persona exists to derive it from. Never read by the rule-based grammar engine — this only configures Stage 5b. Plain type names, not regex: text, currency (or $), decimal, date, integer.

// pack.json
"vision_defaults": {
  "standard_invoice": {
    "fields": { "account_number": "text", "total_printed": "currency" },
    "tables": {
      "line_items": { "date": "date", "description": "text", "amount": "currency" }
    }
  }
}
Why not a second block in persona.json? A row_group selector already declares everything Gemini needs — table_anchor for identity, columns for names + expected shape, column_headers for labels. A hand-written second copy would duplicate that and could silently drift from the real selector. vision_defaults exists specifically for the case a selector can't cover: a vendor with no single fixed layout to anchor against at all.

Library telemetry

// what happened on real traffic, not the offline eval

Distinct from replay-gold/accuracy-report below (a fixed, hand-labelled set): this is what build_pipeline() actually saw on live documents. Off by default — a caller who never asks gets zero disk-write side effects, exactly like today. Opt in with one keyword.

Off default

No file, no handler, no side effect — build_pipeline(vision=…) behaves exactly as it always has.

telemetry=True

One compact JSON line per processed document, appended to var/logs/docintel.jsonl — a 10MB rotating file, 5 backups kept.

telemetry="path.jsonl"

Same thing, your own path — an explicit string overrides the default, same convention DOCINTEL_TELEMETRY_LOG and every other path resolution in this project already follows.

record = pipeline.process(document_id="inv-1", source_path="invoice.pdf")
# writes: {"logged_at":"2026-08-31T09:12:03Z","document_id":"inv-1",
#          "disposition":"processed","lane":"high","doc_type":"invoice",
#          "sender_fingerprint":"acme_widgets|acme_widgets","review_flag":false,
#          "regen_flag":false,"extraction_route":"5a_cached",
#          "mean_confidence":0.94,"elapsed_ms":42.3}
Fail loud at setup, swallow at runtime. A path that can't be created (bad permissions, a missing drive) raises immediately when build_pipeline() is called — a configuration mistake should never process silently. Once processing has started, a per-record write failure never breaks the document it was logging, or changes its disposition — telemetry is diagnostic, never a correctness dependency. One warning logs the first time this happens, not once per document.

Three ways to read it back — all in docintel.telemetry, all reads, never writes:

FunctionAnswers
aggregate(since_days=…)The trend: dead-letter rate, escalation rate (share of documents that reached vision), mean confidence across the window.
problem_records(since_days=…)The actual documents behind that rate — every one that dead-lettered, or landed in the review/low lane.
sort problem_records() by elapsed_ms / mean_confidenceNo separate API — both numbers are already on every logged record. Sort either way to see what's slow, or what's inaccurate.

Same log docintel telemetry-report reads (see Command-line operations) — this is the library-caller path to the exact same data, for a process that never shells out.

Verify one specific dead-lettered document

A dead letter is never a crash — it's a real, emitted record, same shape as any other. Three fields answer "what happened":

FieldTells you
record["disposition"]Confirms it — "dead_letter" means some stage raised an exception. The document is never silently dropped; it still produces exactly one record.
record["reason"]The exact exception message — e.g. "LibreOffice ('soffice') is not installed or not on PATH". This is almost always specific enough to act on directly.
record["events"]The full trace of what ran before it died — every stage that completed, in order, up to the one that failed.
checking one documentrecord = pipeline.process(document_id="bad-001", source_path="corrupt.pdf") if record["disposition"] == "dead_letter": print(record["reason"]) # why print(record["events"]) # what ran first

For documents waiting on a human rather than dead-lettered outright, docintel queue-status reports how many are open and the oldest one's age — built for a cron job, exits non-zero only past an age threshold you set.

Confidence & thresholds

// how "is this good enough" gets decided, automatically

Every field gets a confidence score: match quality (did the anchor register, the pattern parse cleanly, the value shape correctly) × every applicable modifier that fired. One multiplicative mechanism, every modifier that applied listed on the emitted record — never a hidden penalty.

Modifier×Fires when
draft_rules0.85The persona's own status is "draft" — see below, this is the one most first-time users hit.
ocr_source0.90The page came from OCR, not a native PDF text layer.
soft_miss0.80The document's layout diverged from what the persona's fingerprint expects.
ambiguous_anchor0.90The anchor text occurs more than once, with no region to disambiguate.
pattern_timeout0.50The regex hit its 50ms budget — usually a sign the pattern is too permissive.

A field must clear 0.90 to count as cleared. A document routes to high only if every field clears that bar and every required field was found at all.

Everything landing in the review lane, and you're sure your selectors are right? Check persona.json's "status" field first. Every new persona defaults to "draft" — an automatic 0.85 penalty on every field, applied regardless of how correct the extraction actually is. A perfect persona still can't reach the high lane until a human promotes it to "active". This is by design: one document proves nothing, and the penalty is what keeps a single unlucky first sample from auto-approving forever after.

spt_metalsHybrid — DataPack + one custom hookA single-vendor pack needing exactly one non-printed fact (weight-tier margins) alongside pure data.
acme_freightPure data — zero PythonA company whose logic is fully covered by the shared op registry — one pack.json, nothing else.

Four genuinely different shapes, and the choice for your own pack depends on exactly one question: does this company need a fact or a rule the page can never print, that no existing op already supplies?

Pure data

One pack.json, a personas/ folder, zero Python. Gets the ladder, claim guard, field sets, aliases, and (new) a vision_defaults block for vendors with no persona at all. Right when a company's logic is fully covered by the shared op registry.

Hybrid

A thin class wrapping a DataPack, adding exactly one hook for a non-printed fact (e.g. SPT Metals' weight-tier margins). ~120 lines, not ~1,200.

Full module

A bespoke Python package (~1,150–1,290 lines): fingerprint resolution, billing-convention tables, reference collection. Right when a company needs several bespoke hooks.

A fifth vantage point, not a fifth shape: the same pure-data pattern authored entirely outside this repo, in your own project — see "A whole new company" in Compose above. This is the only path a real adopter actually has; the table above is teaching material, not a shipped default.

Writing classification — pack.json

// which company, which document type

A pack claims a document when any rule holds and no veto holds, then an ordered ladder of rungs — first whose condition holds wins — decides the doc_type. Both are plain JSON; nothing here is Python.

The company-level fields — every key at the top of pack.json:

name

The pack's own slug — matches its folder name. What shows up in telemetry and CLI output when a document routes through it.

default_currency

The fallback when infer_currency's whole ladder (ISO code → symbol → tax regime → vendor address) comes up empty. Applied last, and flagged currency_inferred_weak when it fires.

doc_types

Every document type this vendor can send — ["standard_invoice", "credit_memo"]. Each name here needs a matching key under fields and, usually, a ladder rung that can reach it.

thresholds

Per-field confidence floor for the "high" (auto-approved) lane — {"total_printed": 0.90}. A field scoring below its threshold routes to human review even if nothing else flagged it.

Which fields exist — the fields block, one entry per doc_type:

all

Every field this doc_type can carry, extracted or not. The complete vocabulary a persona's field keys are checked against (validation rule V1).

required

Must be covered — by a selector, or by an op that supplies it — or the persona write is rejected outright unless its status is "draft" (V13).

any_of

At least one field from this group must be present. For a vendor that prints either a PO number or a contract number, never guaranteed to print both.

derived_only

Computed by an adjust op, never printed as a standalone value a selector could point at — amount_payable is the standing example. A selector naming one of these is rejected (V10), whatever document it's tested against.

{
  "name": "acme_widgets", "default_currency": "USD",
  "doc_types": ["standard_invoice"],
  "thresholds": { "total_printed": 0.90 },
  "fields": {
    "standard_invoice": {
      "all":          ["vendor_name", "invoice_number", "total_printed", "prior_balance", "current_charges", "amount_payable"],
      "required":      ["vendor_name", "invoice_number", "total_printed"],
      "any_of":        [],
      "derived_only":  ["amount_payable"]
    }
  }
}
markers

A name/address specific enough that no other business prints it — the primary guard for an AP department claiming by bill-to.

corroborated_markers

A weak marker (a bare ZIP) that only counts alongside a second co-occurring token — avoids over-claiming on the weak marker alone.

alias_table

Claims by sender, reading the pack's own vendor alias table — compiled once at load, so it's the shipped table only. DOCINTEL_EXTRA_PERSONAS_DIR's overlay does NOT reach this (tested) — a brand-new carrier needs a real table edit to be claimed, not just an overlay file.

roster_on_short_line

A client name, but only on a short line (a bill-to block) — not a line-item description that happens to mention the client.

Vetoes exist because a marker can be present for the wrong reason: every_marker_hit_in_block refuses the claim if every marker hit sits inside a SHIP TO block — a delivery address says where goods went, not who owes the money.

"claim": {
  "rules": [
    { "kind": "markers", "scope": "primary", "values": ["ACME WIDGETS", "ap@acmewidgets.example"] }
  ],
  "vetoes": [
    { "kind": "every_marker_hit_in_block", "anchor": "\\bship\\s*to\\b" }
  ]
},
"ladder": {
  "default": "invoice",
  "rungs": [{
    "name": "credit_memo_title", "doc_type": "credit_memo",
    "when": { "all_of": [
      { "signal": "title_near_top", "params": {"pattern": "credit memo", "max_words": 7, "max_line_index": 10} },
      { "not": { "signal": "money_table_present" } }
    ]}
  }]
}

All 12 signals a rung's when can name (composed with all_of / any_of / not):

SignalParamsAsks
pattern_in_scopepattern, scopeDoes this regex appear anywhere in scope's text?
short_label_linepattern, max_wordsOn a line no longer than max_words? (a banner, not buried prose)
title_near_toppattern, max_words, max_line_indexA genuine title: short AND near the top of page 1?
text_near_toppattern, max_line_indexNear the top, no length limit — a letterhead block.
label_with_corroborating_valuelabel, same_line/next_line predicateIs a label match backed by a real value near it?
all_matches_negativepattern, scopeMatches at least once, and every match is negative?
role_shapeprimary_exactly, supporting_at_leastDoes the page-role shape match (e.g. 1 primary + ≥1 supporting)?
shared_pagination_footer—Does every page share one "N of M" footer sequence?
money_table_presentmin_money_tokensUsed as a NEGATIVE: a titled "statement" with a charges table is still a bill.

noise_ratio_abovethreshold, role, ocr_onlyDoes a page read as handwriting rather than print?
distinct_printed_aliases_at_leastcount, scopeDoes the alias table match ≥ count distinct printed names?
Fail-loud, at load time. An unknown signal name, region, or misspelled param raises the moment the pack loads — never a rung that silently never fires.

A scanline_selector reads the OCR-A digit line printed along a remittance stub's edge. The 14 validation rules (V1–V14) — run at persona-write time, any single failure rejects the WHOLE write:

V1Every field is in the pack's registered field set for that doc_type.
V2Every adjust op is registered (base + pack).
V3Every region is in the closed enum.
V4Every pattern is a named pattern or passes the restricted-regex rules.
V5A selector with a non-unique anchor and no region is rejected.
V6A bare-digit regex needs a narrowing region or column_headers.
V7scanline_selector.asserts[].field is within the permitted set.
V8sub_group nesting depth ≤ 1.
V9row_count is a range, never an equality.
V10No selector produces a field the pack marks derived_only — the F1 footgun guard.
V11Total serialized persona size ≤ 64 KB.
V12few_shot_examples ≤ 3 entries, none from a flattened_annotations document.
V13Every required field is covered — by a selector, an op, or the persona is draft-only.
V14A pattern capturing only fixed text needs an anchor/region — no anchor may restate a captured value.

Run explicitly with docintel validate-persona <persona.json> --pack-file <pack.json> — it does not run automatically at docintel process startup.

Troubleshooting — real gotchas, first-time mistakes included

Found two ways: in code review against real invoices, and in real first-time onboarding. Both kinds are here together.

A field grabbed the wrong text
region: "near-anchor" is a wide box (300pt right, 40pt below the anchor) — a label at the same height in a neighboring column can leak in. The "text" pattern makes this worse: it accepts whatever candidate it sees FIRST. Fix:use a targeted regex instead of the generic shortcuts. For a party name, an ANCHORED Title Case shape (^([A-Z][a-z]{1,15}\.?(?: [A-Z][a-z]{1,15}\.?)?...)$) rejects an all-caps label like INVOICE NO. outright, letting the pattern loop fall through to the real value on the next line.
A date field came back empty
The named "date" pattern only parses month-first strings (Aug 19, 2026). A day-first date (19 Aug 2026) silently fails — the field is missing, not wrong. Fix:a plain regex instead — ([0-9]{1,2}\s{1,3}[A-Za-z]{3,9}\s{1,3}[0-9]{4}) — records the raw printed text rather than failing to normalize it.
A brand-new carrier isn't claimed, even with a correct persona in the overlay
If your own pack's claim rule is kind: "alias_table", that rule compiles once at load from the table you passed it — DOCINTEL_EXTRA_PERSONAS_DIR's overlay reaches persona lookup and fingerprinting, but never that claim decision itself. (This is the real gap the reference digitaldirection example was built to surface — see Vendors above.) Fix:either the carrier already matches a roster_on_short_line secondary rule, or add it to your pack's own alias table — a genuine code/data change, not something the overlay alone can widen. A markers-based claim guard (bill-to identity, never the sender's name) doesn't have this gap at all. Check your pack's claim rule kind before assuming the overlay is enough.
Every document classifies as the same doc_type, no matter what it actually is
Your ladder has no rung for the other types — or only a "default". The ladder is opt-in per type (Step 1b): write one rung per document type you need distinguished, using a real printed signal from that type (usually title_near_top). This is the most common first-config gap, not a library limitation.
A custom field only extracts well "sometimes," and I ended up scripting around it
Stop and go back to Step 2's anchor/region/pattern question. A script bypasses validation, scoring, and confidence entirely — it isn't faster, it's an untracked second system. If a field genuinely doesn't fit the grammar, name the exact gap (which region, which pattern) rather than routing around it.
Everything from a brand-new persona lands in review
Normal — see Confidence & thresholds above. "status": "draft" applies automatically and can't be bypassed. Promote to "active" once you've checked real coverage against a few documents, not just one.
A document dead-lettered and I don't know why
Don't guess — read record["reason"]. It's the exact exception message, almost always specific enough to act on directly (a missing dependency, a corrupt file, an unsupported extension). record["events"] shows every stage that completed before the failure, if the reason alone isn't enough context.
.docx (or .xlsx) keeps dead-lettering with a LibreOffice error
soffice isn't installed or isn't on the host's PATH — see File formats. .docx has no fallback and needs LibreOffice installed to process at all. .xlsx is the one exception: it should degrade to the pure-Python fallback automatically rather than dead-lettering — if it's still failing, that's worth reporting as a real bug, not a config gap.

Checklist — before you call a vendor "onboarded"

  • pack.json has a claim rule that actually matches your sample document, and a ladder rung for every doc_type you need distinguished — not just default.
  • persona.json has a selector for every field your team needs, each validated with docintel validate-persona, zero errors.
  • No field is targeting amount_payable or another derived value directly.
  • Run against --vision fake first — fields come back right with zero AI calls before you spend anything on live.
  • Checked record["derived"], not record["fields"], for anything business-logic-computed.
  • Ran against more than one real sample — a persona proven on one document is still "status": "draft" for a reason.
  • Tested with every format this vendor actually sends, not just the one sample PDF — classification and extraction don't change per format, but confirm it rather than assume it.
  • docintel replay-gold run at least once if this vendor has gold fixtures, confirming nothing regressed.
  • Know how to check a dead-lettered document before you need to — record["reason"], or telemetry.problem_records() if logging is on.

Limitations — read before you commit a vendor to this

A features list makes any library look flawless. Everything below is a real, current boundary — verified directly against this project's source and its own internal review, not a generic disclaimer. Each one is marked by kind: architectural boundary — by design, not going to change — known gap — genuinely unbuilt, could be closed later.

LimitationKindDetail
Line-item tables don't span pagesknown gapA line_items selector only reads rows on its anchor's own page. Rows that continue onto page 2 are lost — no region trick works around this today.
alias_table vendor claiming can't be extended without a real editboundaryThat claim rule compiles its vendor list once at pack load. DOCINTEL_EXTRA_PERSONAS_DIR's overlay reaches persona lookup fine, but not this one claim decision — a brand-new carrier needs the shipped table itself edited. markers-based claiming has no such gap.
.docx has no LibreOffice-free fallbackboundaryWithout soffice on PATH, every .docx dead-letters outright. .xlsx is the one format with a pure-Python fallback — .docx doesn't get the same treatment.
Hard caps on persona size and few-shot examplesboundaryA persona over 64KB serialized, or with more than 3 few_shot_examples, is rejected outright at write time (V11/V12) — deliberate, not negotiable per-vendor.
Human review never auto-writes new extraction rulesboundaryStage 5c only enqueues a job for a human to look at. Turning an accepted correction into an updated persona is a separate, human-run command — docintel promote-correction — never automatic.
Web UI sat outside the last hardening passknown gapEvery fix in the project's 15-task safety/reliability review deliberately avoided touching src/docintel/webui/. Anything it inherited (like the pdfium thread-safety lock) is a side effect, not something tested against the web UI directly.
Persistent-state paths aren't centrally configurable yetknown gapvar/jobs.sqlite3 and var/logs/docintel.jsonl each resolve independently, with separate env-var overrides and no single configurable root. A fix is drafted, not yet built.
The real-pack fixture suite can't fail CI todayknown gapThe 245 tests against real vendor packs run in CI as a non-blocking step (continue-on-error: true) — a regression there won't fail a build yet, by deliberate choice while its baseline gets established.
The review-queue store is single-nodeboundarySQLiteJobQueue's own docs describe it as serving one reviewer-facing web UI, not a distributed system — nothing coordinates across multiple worker processes or machines.
The gold corpus is intentionally far from all-passingboundaryCI gates on regression vs. the last main-branch run, never on an absolute accuracy bar — because the hand-labelled corpus itself doesn't clear 100% today, and pretending otherwise would just teach people to route around CI.
Two more worth knowing, softer but real. Nothing in the library enforces a spend or request ceiling on --vision live — rate-limiting and cost control against the Gemini API are entirely the caller's own responsibility. And a vendor whose layout drifts from what a persona expects gets a confidence penalty (soft_miss, ×0.80) — there's no automatic detection that a vendor now has two distinct layouts needing two personas; that judgment call is still a human's to make.

How to read this

  • One front door: build_pipeline(vision=…) returns a Runner. Pick a Vision mode and whether you're loading Packs beyond the shipped four — then layer in optional features.
  • The two extension points compose independently: DOCINTEL_EXTRA_PERSONAS_DIR adds a vendor to a pack that already ships; extra_packs= adds a whole new company. Neither ever touches the installed package, so pip install --upgrade can't wipe them.
