```

**Anchor text, quoted from the document's real text layer** (via `pdfplumber`
word extraction, not assumption): `VERITIV OPERATING COMPANY` appears exactly
twice on page 1 — once as the letterhead at (x=63, y=92.7): `VERITIV` /
`OPERATING` / `COMPANY`, and once as the remittance-stub payee line directly
above the P.O. Box, at (x=342, y=151.2), immediately followed on the next two
lines by `P.O. BOX 409884` (y=160.2) and `ATLANTA, GA. 30384-9884` (y=169.2).
`anchor_occurrence: "last"` resolves to the second (remit) occurrence instead
of the default first (letterhead).

**Why this is a template feature, not an accident of this invoice.** Printing
the payee's own name as the running head of its own remittance stub — "make
the check out to X, mail it to this address" — is standard AP remittance-stub
layout, the same convention this same persona already relies on for
`vendor_address` (which anchors on the *first* occurrence of this identical
phrase to read the letterhead address below it). It is boilerplate scaffolding
generated by the billing system on every invoice, not data that varies with
the invoice period or amount — unlike the account number or invoice date,
which do vary and which I explicitly avoided anchoring on for exactly that
reason (see the rejected EDCO attempt below).

Before value: `ATLANTA, GA. 30384-9884`
After value: `P.O. BOX 409884, ATLANTA, GA. 30384-9884` — matches gold
`P.O. Box 409884, Atlanta, GA 30384-9884` under the `address` comparison
(alphanumeric-only), **PASS**.

Scorecard after this change alone: **203/263**, veritiv document rose 19/31 →
20/31. Exactly +1, as required.

The `LABEL_BLOCK_RIGHT = 300pt` column window from the remit occurrence's x0
(342) reaches into a third column at x=527 (`Remit Payment` / `To This
Address`, an annotation printed beside the stub) — this was the specific risk
flagged in a prior exploratory commit (`ba3194a`). It did not bite here:
`column_cut` found the ~85pt real gutter between the address text (ending
~442) and that annotation (starting ~527) and cut there, so the captured block
is clean. Verified empirically, not assumed.

```

**Anchor text, quoted from the document's real text layer:** page 1 (the sole
`primary` page — pages 2-4 are `supporting`) carries the token `WINDSTREAM`
(all-caps, no trailing punctuation) in exactly two places: mixed-case
`Windstream` at (x=36, y=457.5) inside the boilerplate paragraph "Windstream
provides online billing at mybusiness.gokinetic.com..." under the `MAIL:`
label, and all-caps `WINDSTREAM` at (x=367, y=701.3), which is the running
head directly above the remittance-stub's `PO BOX 9001908` (y=711.0) and
`LOUISVILLE, KY 40290-1908` (y=720.6). (`Windstre`/`am` at y=78.5 and

against `page.extract_words()`, not assumed from `_norm`'s behavior.)
`anchor_occurrence: "last"` reaches the second (remit) occurrence.

**Why this is a template feature, not an accident of this invoice.** Every
telecom remittance stub in this corpus prints the carrier's own name as the
header line of its own return-mail block (same convention as veritiv above) —
this is how the payee identifies itself on the tear-off portion independent of
which specific Windstream/Kinetic entity or local carrier name appears
elsewhere on the bill (the "detach" line even names a *different* legal
entity, `OKLAHOMA WINDSTREAM, LLC`, showing the two are not the same string
and must not be conflated). The boilerplate `MAIL:` paragraph that produces
the first, wrong "Windstream" occurrence is themselves also fixed template
copy on every Windstream/Kinetic bill, so the two-occurrences-last-wins shape
should hold across other invoices from this same sender fingerprint.

Before value: `LOUISVILLE, KY 40290-1908, AAAATTFDFTAADDFTDTDDADDTTFAAAFFTDTAAFATTDFTDDTATADDDFDAADTTATTFTD`
After value: `PO BOX 9001908, LOUISVILLE, KY 40290-1908, AAAATTFDFTAADDFTDTDDADDTTFAAAFFTDTAAFATTDFTDDTATADDDFDAADTTATTFTD`
Expected: `PO Box 9001908, Louisville, KY 40290-1908`

The re-anchor **did its job**: the previously-deleted `PO BOX 9001908` line is
recovered. The assertion still fails because a separate defect remains: the
document's own text layer prints a 64-character junk run
(`AAAATTFDFTAADD...`) on its own line just below the ZIP, at (x=367,
y=725.4) — only 4.8pt below the address line, well inside `label-block`'s own
gap tolerance, and in the same x-column as the address, so nothing in the
region/anchor vocabulary separates it from the address it sits under. This
matches exactly what the brief predicted and instructed against: I did not add
a rule that strips this specific string, since that would be a cleanup rule
fitted to one document's noise — precisely what GUARDRAIL 9 exists to catch,
and what the brief explicitly forbade. Recorded as a separate, distinct
finding; the assertion is left failing.

### edco — NOT FIXED, persona left unchanged (structural blocker)

File: `src/docintel/packs/northstar/personas/edco.json` — **no net change**
(see git diff; reverted to original after two failed attempts, both run
through the real pipeline, not simulated).

Current (unchanged) selector:
```json
{
  "field": "remit_address",
  "anchor": "P.O. BOX 5488",
  "region": "label-block",
  "pattern": "text_block",
  "adjust": ["join_lines_comma"],
  "required": false
}
```

This is still the bug named in the brief — the anchor is the value's own
first line — but every alternative anchor I could construct from the
document's actual text layer made the result **worse**, not better, so I did
not commit any of them. Detail:

**The page's structure.** EDCO's remit block prints:
```
y=164.9  EDCO WASTE & RECYCLING SERVICE      (x=353.6, remit column)
y=176.9  P.O. BOX 5488                        (x=353.6)
y=188.9  BUENA PARK, CA 90622-5488            (x=353.6)
```
`EDCO WASTE & RECYCLING SERVICE` — the only printed text sitting above the PO
Box line in that column — is **not unique on the page**: it is the exact same
run printed identically three times: the page's own letterhead header
(y=33.3, x=51.2), this remit occurrence (y=164.9, x=353.6), and the
`vendor_address` block lower on the page (y=304.0, x=44.0). `anchor_occurrence`
only supports `"first"` and `"last"`, not "the second of three" — and here the
occurrence we need is the *middle* one. I tested both, directly through the
real `Executor`, not by hand-simulation:

- `anchor_occurrence` default (`first`) → resolves to the letterhead (y=33.3,
  x=51.2, a LEFT-aligned occurrence) → `label-block`'s column window follows
  that x0, landing on the vendor's own address block, not the remit one.
  Verified result: `224 S LAS POSAS RD, SAN MARCOS, CA 92078` (EDCO's own
  address — wrong field's content entirely).
- `anchor_occurrence: "last"` → resolves to the `vendor_address` block
  (y=304.0, x=44.0, also LEFT-aligned) → same wrong result:
  `224 S LAS POSAS RD, SAN MARCOS, CA 92078`.

Both are strictly worse than the current (buggy) output — they return the
vendor's own mailing address instead of a remit address with only its first
line missing. I reverted rather than commit a regression.

I also tried reaching further up the same column to the account/date header
(`25-3A 077087 04/30/25`, printed once at y=56.9 and, as a group, nowhere else
verbatim), which does sit at the same x as the remit column and is
unambiguous. This does position `label-block` correctly, but the intervening
line at y=104.9 in that same column — the invoice's headline total `367.96` —
falls inside the block's gap tolerance and is not part of the anchor's own
skip set, so it leaks into the capture:
`367.96, EDCO WASTE & RECYCLING SERVICE, P.O. BOX 5488, BUENA PARK, CA
90622-5488` (verified via `replay-gold`, then reverted). Worse still, that
anchor text embeds the invoice's own account number and date — exactly the
per-document values the brief told me to avoid anchoring on, since they don't
recur on the vendor's next invoice.

**Conclusion:** EDCO's remit block has no printed label above it that is both
(a) unique on the page and (b) reachable without crossing a dynamic value.
This is not fixable by re-anchoring under the current grammar's
first/last-occurrence vocabulary — it would need either a way to select a
specific (non-first, non-last) occurrence, or a region that can skip over an
intervening line the way `text_block` skips the anchor's own words. Both are
schema/engine changes, out of scope for this persona-only task. I left the
persona and the `ANCHOR_IN_VALUE_DEBT` entry for `("edco", "remit_address")`
untouched rather than force a worse or invalid result.

## Self-review

- **Does any selector end up restating its value?** No. `VERITIV OPERATING
  COMPANY` and `WINDSTREAM` are both distinct from their respective
  `remit_address` values (a P.O. Box / city / state / ZIP string) — neither
  anchor text appears inside the captured value, confirmed by the same
  `_alnum` substring check `test_no_anchor_is_part_of_the_value_it_captures`
  uses, which is why both personas could leave `ANCHOR_IN_VALUE_DEBT`.
- **Does each anchor read something the document genuinely prints?** Yes —
  both were located by direct `pdfplumber` word extraction against the real
  PDFs (`docs/_AP Invoice 715-33905296 ... .pdf`,
  `docs/Windstream_041069076_07222025_BILL.pdf`), not inferred from
  expectation of what a "typical" US invoice says.
- **Would this plausibly work on the vendor's next invoice?** For both: yes,
  with the caveat that it depends on the same billing-system template
  continuing to print the payee's own name as the remittance stub's running
  head, which is boilerplate scaffolding rather than per-invoice data — the
  same class of feature `vendor_address` already anchors on for its own
  (first) occurrence of the identical phrase. It would NOT survive a vendor
  reformatting its remittance stub to omit that running head, but no anchor
  strategy would survive that.
- edco was left alone rather than force a selector that only "matched" —
  both alternatives I tried actively regressed correctness (returning the
  vendor's own address instead of a partial remit address), so per the
  brief's instruction I reverted rather than commit a plausible-looking but
  wrong selector.

## Issues or concerns

- **EDCO's `ANCHOR_IN_VALUE_DEBT` entry is a real, currently-unfixable
  limitation** of the anchor grammar's first/last-occurrence model, not a
  postponed task. Fixing it for real would need either an nth-occurrence
  selector or a region that can skip an intervening non-anchor line — both
  are engine changes outside this task's scope (persona JSON only), and I did
  not make them.
- Windstream's OCR-junk suffix is a data-quality defect in the source PDF's
  text layer (a private-use/garbled font run), not a persona defect. It is
  now clearly separated from the anchor-deletion bug this task targeted, and
  it remains as a known, documented gap rather than something forced to pass.
