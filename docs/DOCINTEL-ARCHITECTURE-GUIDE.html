Document Intelligence · Architecture & Operator's Guide

How it works, how to run it, and how to configure the next vendor

One reference for the whole system: the pipeline that turns a PDF into a structured record, the two ways to run it, the human-review loop that catches what the rules can't decide, and — the part that matters most once this is live — exactly what to touch when a new vendor or a new client company arrives.

Overview

The central design claim: what to extract is a specification, not code. A document arrives, gets read (native text or OCR), gets claimed by whichever client company it belongs to, gets classified into that company's own document-type vocabulary, and then either matches a saved reading rule (no AI call) or escalates. Every document that goes in produces a record coming out — nothing is ever silently dropped.

flowchart TD A["📄 Document arrives"] --> B{"Readable file type?"} B -- No --> Z["Skipped, reason on the record"] B -- Yes --> C["Read every page — native text or OCR"] C --> D{"Claimed by a configured company?"} D -- No --> Y["Tagged unclaimed_document — still emitted"] D -- Yes --> E["Classify using that company's own doc_type ladder"] E --> F{"Known sender + layout?"} F -- "Yes, most of the time" --> G["Apply saved reading rules — no AI, no cost"] F -- No --> H["Ask a vision model"] G --> I["Extract the fields that company asked for"] H --> I I --> J["Apply business rules for values that aren't printed anywhere"] J --> K{"How sure are we?"} K -- "Everything checks out" --> L["✅ Auto-approve"] K -- "Some doubt" --> M["👤 Human review queue"] K -- "Can't tell, won't guess" --> M classDef good fill:#e1f3e7,stroke:#1f7a45,color:#123a20 classDef human fill:#fdf1d9,stroke:#9a6b0c,color:#4a3505 classDef neutral fill:#ece9e1,stroke:#8b93a0,color:#2a2f38 class L good class M human class Z,Y neutral

Three layers, and only the top one changes when a new company or vendor arrives:

The engine

Knows nothing about any document type. Reads pages, finds values by position and pattern, scores confidence, routes. This never changes per client.

The shared operation library

A closed, named vocabulary — 26 field/document operations, ~12 classification signals, the record contract. Extending it is a reviewed code change with a test.

The specification

Pure JSON, per company and per vendor — which document types exist, which fields matter, where they sit, which business rules apply. This is what you author.

Architecture

The 10 stages

Every document walks the same fixed pipeline, in src/docintel/pipeline/stages/. The Runner wraps every stage so a crash anywhere still emits a dead-letter record rather than losing a document silently.

#StageModuleWhat it does
1Intakes1_intake.pyDiscovers files, assigns a stable document id.
2Attachment filters2_filter.pyAllow-lists the file type (PDF only), reads every page — native text or OCR — labels pages primary/supporting.
3Classifys3_classify.pyDecides which company claims the document, then that company's doc_type via its own JSON ladder.
4Persona lookups4_persona.pyFingerprints the sender/layout (pack|vendor), looks up a saved persona.
5aApply cached ruless5a_cached.pyRuns the persona's saved selectors. No AI call — this is the fast lane, and it's where almost every document stops.
5bVision one-shots5b_vision.pyEscalates to Gemini only when 5a can't cope or no persona exists — see Gemini vision extraction for the exact decision logic.
5cAgent escalations5c_agent.pyA hard-miss sender (no persona, weak confidence) queues a persona_authoring job for a human — see Review queue.
6Capture fieldss6_capture.pyNormalizes values, runs the persona's declared adjust ops (derivations, cross-checks), resolves vendor identity.
7Confidence gates7_gate.pyAssigns a routing lane — high / medium / review / low — and queues a prior_balance_basis job when a vendor's billing convention is unknown.
8Emit records8_emit.pyValidates against the record contract, emits. Always runs, even on a dead letter.

What file types are accepted

Stage 2 checks the file suffix against an allowlist before anything else runs, built from one shared constant so it can never drift from what the directory-walking intake adapter and the web UI's own upload gate each independently check: 

# src/docintel/extract/convert.py
IMAGE_SUFFIXES  = {".png", ".jpg", ".jpeg", ".tiff", ".tif", ".bmp", ".gif"}
OFFICE_SUFFIXES = {".docx", ".xlsx"}
ACCEPTED_SUFFIXES = {".pdf"} | IMAGE_SUFFIXES | OFFICE_SUFFIXES

Anything outside this set is disposition: "skipped" with a plain-English reason on the record ("file type .zip not in allowlist"), never silently dropped and never crashed on — the same "every document that goes in produces a record coming out" invariant from the Overview, applied to the one gate that runs before any of it.

flowchart TD A["File arrives"] --> B{"Suffix in ACCEPTED_SUFFIXES?"} B -- No --> Z["Skipped, reason on the record"] B -- "Image (.png/.jpg/.tiff/...)" --> C["Pillow wraps it as a PDF page(s)"] B -- "Office (.docx/.xlsx)" --> D["LibreOffice headless renders it to PDF"] B -- ".pdf already" --> E C --> E["load_document() — completely unmodified"] D --> E E --> F["Everything downstream: OCR routing, grammar, personas, scorecard"] classDef good fill:#e1f3e7,stroke:#1f7a45,color:#123a20 classDef neutral fill:#ece9e1,stroke:#8b93a0,color:#2a2f38 class F good class Z neutral

Conversion at the intake boundary, not a second extraction path. An image or an Office document is converted to a real PDF before Stage 2 does anything else, in extract/convert.py:

FunctionHowWhy this way, not native parsing
convert_image_to_pdfPillow (already a dependency — no new install). Wraps a raster image, or every frame of a multi-frame TIFF/GIF in order, as PDF page(s).A wrapped image reads back with char_count == 0 — exactly the existing signal that already routes a page to OCR, so the OCR path needed zero changes.
convert_office_to_pdfShells out to LibreOffice headless (soffice --headless --convert-to pdf), one throwaway -env:UserInstallation profile per call so concurrent conversions can't lock or corrupt each other's shared profile.grammar/regions.py's selectors (same-row, near-anchor, totals-block) are calibrated against measured geometry from real rendered PDF pages. A DOCX's flow layout or an XLSX's cell grid has no honest analogue — synthesizing word coordinates from paragraphs or cells would be a second, weaker extraction model nobody measured. Converting first means Office documents get real geometry for free, and nothing downstream changes at all.

A conversion failure raises PermanentError/TransientError — the same discipline the OCR path's own _ocr_and_check_complete already uses — so it dead-letters that one document with a clear, actionable reason (a malformed DOCX, a missing LibreOffice install) rather than crashing the run. LibreOffice itself is a system dependency, not a pip package — install it on any host that needs to accept Office documents; its absence fails loudly and per-document, so it's safe to notice at deploy time rather than a hard build-time requirement.

Within "PDF", two very different documents — still true A PDF with a real text layer is read natively; a scanned PDF (or a wrapped image, or a converted Office document with no extractable text) is read via OCR — text_source on the emitted record says which. The native-vs-OCR decision happens one level deeper, inside extract.normalize.load_document, completely unaware that some of its inputs started life as something other than a PDF.

Email containers — one input, many documents

The invoice is almost always an attachment, not the email body — so a `.eml`/`.msg` never reaches Stage 2 itself. It is unwrapped one layer above the pipeline entirely, into one ordinary document per attachment.

The one invariant this had to respect Runner.process(document_id, source_path) -> dict is a strict, machine-checked 1:1 elsewhere in this codebase — one call, one record, never a list (count(intaken) == count(emitted)). An email genuinely can contain several documents, so the expansion happens one layer above the Runner, never inside it — the exact same seam FilesystemIntake._walk already uses to turn one directory into many items, applied to one archive file instead of a directory tree.
How
Whereadapters/intake/email.py's EmailIntake, implementing the same IntakeSource protocol as FilesystemIntake — the CLI's existing per-item loop already calls runner.process() once per yielded item, so it runs N times for one email with zero changes to the loop itself.
Formats.eml parses with the stdlib email module — no new dependency. .msg (Outlook's proprietary format) needs extract-msg, its own optional extra: pip install 'docintel[email]'.
document_idA stable hash of the email's own key (its Message-Id header, or a content hash when absent) plus the attachment's index/filename/size — the same shape FilesystemIntake._stable_id already uses, so redelivery of the identical email never mints new ids.
NestingNot supported, on purpose. A nested container attachment (another .eml, a .zip) is yielded like any other attachment, not recursed into — its own suffix isn't in ACCEPTED_SUFFIXES, so Stage 2 rejects it cleanly for free.
A parse failure, or zero attachmentsFalls back to yielding the original email path as one item, so it is still counted and still visible on a skipped record — never silently vanishes.
Where it stopsCLI only, for now. The web UI's /process route is built around exactly one upload producing exactly one result screen — supporting 1:N there is a real UI design question, sequenced after the CLI path was proven.

One more piece the conversion work above needed: JobContext.readable_path. When Stage 2 converts a non-PDF input, source_path is deliberately left pointing at the original file — crosscheck_filename reads its basename to compare an amount embedded in the original filename against the printed total, and a converted file's throwaway temp name would silently break that. Any stage that needs to actually open the document's bytes (Stage 5b's Gemini call) reads ctx.readable_path or ctx.source_path instead.

The fields / derived split

The single most important thing to understand about the output record. A value lives in exactly one of two places:

  • fields.* — what was read off the page. Printed evidence, untransformed.
  • derived.* — what was computed or resolved. Alias tables, arithmetic, inference.
Why this matters A field being null in fields does not mean it's missing — it may be resolved in derived instead. Any code reading only record["fields"] will produce false alarms. Always check fields first, then fall back to derived, for any given field name.

Confidence lanes

LaneMeaningFlags
highEvery field cleared its confidence threshold.audit sample only
mediumSome fields fell short, but the shortfall is explained (e.g. a scan).review
reviewSomething mandates a human look regardless of confidence — a forced tag, or a business-rule refusal.review
lowSystemic collapse — the persona's rules no longer fit this document, not just this one field.review + regen

The gate never raises or clears review_flag itself for reasons unrelated to confidence — that flag can also come from upstream (a hard-miss sender, or a business-rule refusal like an unresolvable prior balance).

Gemini vision extraction

Stage 5a (the saved selectors) is free and handles almost every document once a vendor has a working persona. Gemini is the fallback for the two cases that aren't that: a sender nobody has configured yet, or a known persona whose reading stopped fitting the document in hand. Nobody chooses this per document — it is fully automatic, decided fresh every time, by four cheap checks against what Stage 5a already produced.

When it runs — the decision logic

flowchart TD A["Stage 5a ran"] --> B{"extraction_route == 5a_cached?"} B -- "No — no persona at all" --> G["Call Gemini"] B -- "Yes" --> C{"Anything extracted at all?"} C -- "No" --> G C -- "Yes" --> D{"2+ fields below confidence 0.50?"} D -- "Yes" --> G D -- "No" --> E{"miss_share ≥ 60% of declared fields?"} E -- "Yes" --> G E -- "No" --> F["Leave the 5a result alone — no AI call"] classDef good fill:#e1f3e7,stroke:#1f7a45,color:#123a20 classDef human fill:#fdf1d9,stroke:#9a6b0c,color:#4a3505 class F good class G human

In code (s5b_vision.py), the whole gate is one line — run() returns immediately unless this is true:

ctx.extraction_route == "5a_cached" and not _collapsed(ctx)

_collapsed(ctx) is true — meaning Gemini runs — under any of these:

ConditionWhat it catches
No persona at allA genuinely first-time vendor. extraction_route never became 5a_cached, because there was no rule set to try. This is the single biggest reason a new vendor's very first document reaches Gemini.
ctx.extracted.match_quality is emptyA persona matched zero fields — as complete a failure as a weak one, just at the other end.
2 or more fields scored below 0.50Individually weak reads. COLLAPSE_THRESHOLD = 0.50.
coverage.assess(ctx).miss_share ≥ 0.60The case confidence alone can't see: a persona declaring 14 fields where 12 come back empty and 2 come back at 0.99 confidence still counts as collapsed. match_quality only ever records a field that produced a value, so the 12 empty ones are invisible to the confidence check above — coverage is the one place that already answers "how much of what was declared came back empty," reused rather than re-invented. DEFAULT_COLLAPSE_SHARE = 0.60.
A fifth, separate escalation — not extraction Stage 5c (agent_escalation) fires only when persona_status == "hard_miss" and Gemini's weakest confidence is below 0.60 (WEAK, a different threshold from Stage 5b's own 0.50). It does not change what gets extracted for the current document — Gemini's Stage 5b answer still ships. It queues a persona_authoring job so a human eventually writes a real persona for next time, and sets review_flag = True. See Review queue.

What it's told: field_hints

A known-but-collapsed persona already knows this vendor's field list and roughly where each value sits — throwing that away and asking Gemini the same generic 4-field question every first-time vendor gets would waste the one piece of vendor knowledge most likely to recover the read. So Stage 5b asks:

CaseFields requestedHints sent
No persona (true first-time vendor)The generic default — vendor_name, invoice_number, invoice_date, total_printedNone — there is no vendor knowledge to draw on yet
Known persona, collapsedThat persona's own full declared field listOne sentence per field, built from the persona's own anchor/region/pattern — e.g. total_printed: labelled "Total Amount Due", in the totals box, a money amount
Caller supplies an explicit field listExactly that list (a test, or the isolated eval-vision suite, which deliberately wants a fixed, vendor-independent set)None — an explicit override always wins and carries no hints

Built by adapters/vision/hints.py (field_names_for_persona, hints_for_persona). Deliberately prose, never the regex itself — an anchor and a region become a sentence a model can act on ("labelled X, just below or beside that label"), not an instruction it cannot run anyway. A field with nothing describable is simply left without a hint, never padded with a vague placeholder.

Why geometry isn't actually the expensive part on this path An external ablation against this same corpus — delete every anchor and region from the prompt, keep only field name, type, and one sentence — moved 1 value in 102 that had a hint at all (10 documents, 256 assertions: 221/256 with hints vs. 219/256 without). What is load-bearing is the field list and its type, not the coordinate-level precision a hand-authored regex selector needs. This is why a brand-new vendor's Gemini path can recover reasonably even before anyone hand-writes a persona for it.

What it's never allowed to decide

The system prompt (adapters/vision/gemini_adapter.py) is one instruction repeated in different words: transcribe, do not interpret. Report each value exactly as printed. Do not do arithmetic — no summing line items, no netting credits, no computing a balance. Do not decide which of several printed totals is the one actually owed; total_printed means the headline number as printed, even if a different number is what should be paid. An unreadable value comes back as an empty string, never a guess.

That boundary is enforced twice, not once — the prompt is a request, not a guarantee:

  1. The response schema

    Every requested field is a plain string; type coercion into currency/date/Decimal happens downstream, in the same coercer a regex selector's pattern already uses — Gemini is never asked to produce a typed value.

  2. adapters/vision/policy.sanitize

    The real boundary. Drops any field name Gemini wasn't asked for (Gemini's schema subset has no additionalProperties: false, unlike the Anthropic path, which makes this check load-bearing rather than a second belt-and-braces net), drops any irregularity flag outside the closed enum, clamps confidence into [0, 1]. A model that invents amount_payable — the exact number the business rules must derive, never read — gets it silently discarded here, every time.

The business decision itself — what's actually payable, which prior-balance convention applies, whether a weight-tier margin was misapplied — happens afterward, in Stage 6/7's real adjust ops, reading whatever Gemini transcribed the exact same way it reads a regex selector's output. Gemini supplies values; code supplies decisions, and only code's decisions are ever tested and recorded with a reason.

Cost guards, because Gemini bills a PDF page as an image plus its text — cost scales with page count, not byte size: MAX_PAGES = 30 (a real 24-invoice sample found legitimate telecom bills running 14–18 pages, so this is deliberately above that evidence, not a guess) and MAX_PDF_BYTES = 15 MB (the inline-part ceiling; bigger needs the Files API). Both are refusals, not warnings — going over either raises a clear, permanent error rather than silently billing for a document nobody decided to send whole.

Real-time notification, as a library

docintel has no inbox watcher or webhook receiver of its own — that's the caller's infrastructure, whatever it looks like — but Runner.process(...) is a plain synchronous call, and build_pipeline() now accepts a caller-built HookRegistry (hooks=) instead of always constructing its own and discarding what a caller registered. Register a beforeEmit hook — the one socket guaranteed to fire after lane/review_flag/regen_flag are already decided, for every emitted record — and a caller knows the instant a document needs a human, inline, with no polling interval to wait out. The channel (email/Slack/webhook) is deliberately left to the caller's own code. Full recipe in the root README.md's "Real-time notification" section; the 8 hook sockets themselves are declared in src/docintel/pipeline/hooks.py (SOCKETS) — see Quick reference.

One Runner per concurrent worker A Runner keeps small mutable per-run state (an in-run duplicate-detection index, a processed-document counter) — safe for one worker calling .process() repeatedly, not safe for two threads sharing the same Runner at once. build_pipeline() is cheap to call again per worker (packs/personas are cached process-wide), so build one Runner per worker and reuse it for that worker's lifetime — never share one across concurrent callers.

The web UI

A single Flask app (src/docintel/webui/app.py) for two jobs: process one document and see the result, and work through whatever's waiting for a human.

/ — upload

Upload one PDF. It runs through the real extraction pipeline (rule engine only — the AI fallback is off in the default runner). You see the classification, the extracted fields with per-field confidence, and a status of Auto-approved or Needs review.

Four outcome screens

Extracted (fields shown, status computed), no persona (nothing configured for this sender yet), collapsed persona (a persona exists but mostly stopped matching — a template redesign), failed (skipped/dead-lettered, with the reason).

The review queue

Two situations escalate to a real, persistent queue (SQLite, var/jobs.sqlite3) instead of just logging a line no one reads:

    Every open job, grouped by kind, with the sender fingerprint, document type, and when it was queued.

Full module — northstar, digitaldirection

A bespoke Python package per pack (~1,150–1,290 lines across ~8 modules): fingerprint resolution, billing-convention tables, reference collection, aliasing. Right when a company needs several bespoke hooks, not just one.

Both directions are gold-labelled (docs/corpus/gold/spt-metals-70921.json, -71104.json) and both score 23/23 on replay-gold.

Configuring a new vendor of an existing company

The common case: northstar or digitaldirection already exists, and a 7th (or 5th) vendor starts billing them. This is a configuration change, not a software release.

  1. Write a persona file

    Drop a new JSON file into src/docintel/packs/<pack>/personas/<vendor>.json. It's picked up automatically — personas are read by directory scan, nothing needs registering. A real, working example (Northstar's DTSS persona, trimmed):

    {
  "sender_fingerprint": "northstar|dtss",
  "doc_type": "standard_invoice",
  "rule_version": "v1",
  "status": "active",
  "field_selectors": [
    { "field": "vendor_name", "region": "top-left", "pattern": "text" },
    { "field": "invoice_number", "anchor": "Invoice #",
      "region": "near-anchor", "pattern": "text" },
    { "field": "invoice_date", "region": "top-right", "pattern": "date",
      "adjust": ["normalize_date_iso"] },
    { "field": "total_printed", "anchor": "Total", "region": "near-anchor",
      "pattern": "currency",
      "adjust": ["resolve_vendor_alias", "resolve_bill_to_alias",
                 "resolve_carried_balance", "derive_amount_payable"] }
  ]
}

  2. Pick a region and a pattern for each field

    A selector is where (region, optionally anchored to a printed label) plus what shape (pattern). Both vocabularies are closed and shared across every pack — see the quick reference for the full lists actually in use.

  3. Add an alias, if the vendor's printed name varies

    If the vendor prints its name more than one way (a letterhead vs. a remittance payee), add an entry to that pack's aliases.py LITERAL_ALIASES dict so every rendering resolves to the same canonical key — and a display name to DISPLAY_NAMES if no selector will ever extract vendor_name directly. Skip this if the vendor always prints one consistent name.

    A real safety net, not just a suggestion sender_fingerprint's vendor half must be a key this alias table actually produces — a shipped test (test_every_persona_fingerprint_names_a_known_vendor) fails immediately in CI if a new persona's fingerprint names a vendor the alias table doesn't know, so forgetting this step doesn't fail silently.

  4. Decide the vendor's prior_balance_basis — or don't, yet

    If the vendor ever prints a "prior balance" or "balance forward," a human needs to have looked at real invoices and decided whether it's gross or net_of_payments. You can add it directly to that pack's hand-maintained PRIOR_BALANCE_BASIS dict in conventions.py (a reviewed code change) — or leave it unset entirely. If it's genuinely unknown at authoring time, the pipeline will correctly refuse to guess, route the document to review, and queue a prior_balance_basis job — a reviewer can confirm it later through the web UI with no further code change. See below.

  5. Validate and test

    Two layers, and they run at different times — worth knowing precisely so a typo doesn't slip through:

    • Structural parsing runs automatically, every time the process starts (inside PackPersonaStore's construction). It catches a missing required key or an unrecognized selector shape — but it does not check vocabularies.
    • Semantic validation (the real security boundary — 13 numbered rules) checks the vocabulary: is this adjust op name actually registered, is this region actually in the closed enum, does a selector target a derived_only field it's never allowed to touch. This does not run automatically at docintel process startup — run it explicitly, either via docs/persona-regeneration/reference/try_persona.py (a reference script built for exactly this) or by adding the new persona to the parametrized test in tests/packs/test_personas_validate.py ("guardrail 5"), which every shipped persona already runs through in CI.

    What a typo actually looks like once you do run it:

    ValidationError: selector[6] (field 'total_printed') names adjust op
'resolve_carreid_balance', which is not registered (V2). A new op is a
business-logic change and needs a PR and an eval, not a persona write

ValidationError: selector[2] (field 'invoice_date') names region 'top-lft',
which is not in the section 2 enum (V3)

    Then run the new persona against a real sample document (docintel process path/to/sample.pdf --json) and check the extracted fields by eye before calling it done.

One thing to know about timing Unlike the billing-convention overlay, a new persona file needs the process to restart (or the CLI to be invoked fresh, or docintel serve to be restarted) before it's picked up — PackPersonaStore parses every persona once, at construction, for the lifetime of that runner.
Start a new persona as "status": "draft" A draft persona applies an automatic 0.85 confidence penalty and can never reach the high lane — every document routes to review while you're still validating field coverage. Every shipped persona must be "active" before merging (a dedicated test enforces this), so promote it once you've checked real coverage.

Onboarding a brand-new client company

Faster start: scaffold, don't hand-author docintel new-pack <slug> --company "..." --doc-type ... [--hints <path>] writes a starting pack.json and persona skeleton for steps 1-2 below — seeded from a generate-persona hint-spec draft if you have one, every selector geometry field left an explicit placeholder. Then docintel validate-persona <persona> --pack-file <pack.json> self-checks the result against the same V1-V14 rules below, before anyone else looks at it. A whole new company can be onboarded as pure data — no Python module at all. acme_freight ships in this repo as exactly that proof: one pack.json, a personas/ folder, zero lines of Python, and a test (tests/packs/test_datapack.py) that fails the day that ever stops being possible.

    Same as an existing pack — one JSON file per vendor, same schema as above.

    A data-only pack gets the classification ladder, tag rules, claim guard, field sets, thresholds, and aliases. It does not get pack-specific hooks — see When you still need Python for exactly what that costs.

Confirming a vendor's billing convention without a restart

This is the one piece of business logic a reviewer can change directly, live, through the web UI — everything else in this guide is a developer's job. It exists because "is the printed prior balance already net of payments, or still gross" is a business judgment about how a specific vendor bills, not something any extraction rule should ever guess.

The hardcoded, audited PRIOR_BALANCE_BASIS table in each pack's conventions.py is always checked first — the overlay is a strictly lower trust tier, exactly for the reason its own code comment states: "a wrong entry in the table is a reviewed code change; a wrong overlay entry is a reviewer's call, correctable the same way."

Writing business logic

"Business logic" in this system is authored in exactly three places, in order of how often you'll touch them.

Claim rules — deciding whose document this is

A pack claims a document when any rule holds and no veto holds. Four rule kinds exist, deliberately closed:

KindUse whenReal example
markersA name or address specific enough that no other business prints it.Northstar guards on its own address: "po box 188 east longmeadow".
corroborated_markersA weak marker (a bare ZIP code) that only counts alongside a second one."ma 01028" only counts if "northst" also appears — a bare ZIP alone claims too much.
alias_tableThe pack claims by sender, and already maintains a vendor alias table — reads it directly, so onboarding a new carrier is a table edit, not a new rule.Digital Direction (a telecom expense manager) claims by carrier, not bill-to.
roster_on_short_lineA client name, but only on a short line — a short line means a bill-to block, not a line-item description that happens to mention the client.Digital Direction's managed-client roster, as a secondary/fallback rule.

Vetoes exist because a marker can be present for the wrong reason. every_marker_hit_in_block is the one shipped today: if every marker hit sits inside a SHIP TO block, the pack does not claim — a delivery address says where goods went, not who owes the money.

The doc_type ladder — deciding what kind of document it is

An ordered list of rungs; the first whose condition holds wins. If none fire, the ladder's own default applies. Rung order is load-bearing — write the more specific test above the more general one. A real rung:

{
  "name": "statement_title_no_table",
  "doc_type": "statement_of_account",
  "when": {
    "all_of": [
      { "signal": "pattern_in_scope",
        "params": { "pattern": "\\bstatement of account\\b", "scope": "primary" } },
      { "not": { "signal": "money_table_present" } }
    ]
  }
}

A condition is a small closed algebra: a named signal, or all_of / any_of / not composing other conditions. Signals used across today's packs include pattern_in_scope, title_near_top, text_near_top, role_shape, all_matches_negative, money_table_present, shared_pagination_footer, noise_ratio_above, label_with_corroborating_value, short_label_line, text_source_is, distinct_printed_aliases_at_least. Adding a genuinely new signal is a code change with a test and a named real document behind it — that's what keeps "declarative" from becoming a second, unreviewed way to write regexes.

Fail-loud, at load time An unknown signal name, an unknown region, a misspelled parameter — each raises when the pack loads, not silently evaluating to false at classify time. A rung that silently never fires is a document type that silently never gets recognized, and this system refuses to let that happen quietly.

When you still need Python

A data-only pack (§above) gets the ladder, tag rules, claim guard, field sets, thresholds, and aliases. It does not get pack-specific hooks — and both shipped packs today need every one of these:

HookWhat it doesCost of not having it
resolve_vendor_fingerprintBuilds the pack|vendor key Stage 4 looks a persona up by.No fingerprint → no persona ever matches → the cached fast lane is unreachable, every document falls to vision or a hard miss.
apply_billing_conventionsSupplies prior_balance_basis from the pack's table (§ above).Without it the F1b refusal fires on every document with a prior balance — no CentraCom-style derivation is possible at all.

Writing one of these means adding a Python module for the pack (the two shipped packs are each ~1,150–1,290 lines across ~8 modules) — a real engineering task, not a config edit. Whether to eventually add a declarative equivalent for these two hook kinds is an open question for this codebase, not yet solved.

Validating & testing a change

  1. Classification is fail-loud automatically

    A pack's claim rules and doc_type ladder are compiled the moment the pack loads (every process start) — an unknown signal name, scope, or malformed condition raises immediately, before any document is processed.

  2. Persona vocabulary needs an explicit check

    Structural parsing runs automatically too, but it only catches malformed shapes — an unregistered adjust op name or an unknown region is not caught just by running docintel process. Run try_persona.py or the shipped-persona test (§above) explicitly before trusting a new persona file.

  3. Run it against a real sample

    docintel process path/to/sample.pdf --json — read the output record by eye. Check both fields and derived.

  4. Score against the labelled corpus

    docintel replay-gold — confirms nothing else regressed. This is the number that matters more than any single document looking right.

  5. Run the test suite

    python -m pytest -q — full pipeline, pack, and grammar tests.

The evaluation layer

Everything above is checked against one thing: a hand-labelled corpus of real documents, each with the correct answer written down in advance. Gold is the only source of truth this project trusts — no test invents its own expected values, and no fixture is ever authored from the pipeline's own output (that would score a system against itself and call it evidence).

Gold fixtures & the scorecard

One JSON file per document in docs/corpus/gold/ — 17 today, one per real (or, for SPT Metals, realistically constructed) invoice. A trimmed real example, spt-metals-70921.json: 

{
  "gold_id": "spt-metals-70921",
  "source_file": "SPT_Metals_Invoice_70921.pdf",
  "pack": "spt_metals",
  "classification": {
    "doc_type": "carbon_bar_invoice", "tags": [], "text_source": "native",
    "page_count": 1, "page_roles": ["primary"]
  },
  "fields": {
    "weight_per_ft": 3.03, "footage": 700, "ship_to_state": "NY",
    "total_printed": 1712.78, "total_weight": 2121.0,
    "weight_tier": "Tier 2", "weight_tier_margin": 1.08
  },

The mistake this project has already made once, and now can't make silently A numeric field whose name is in neither MONEY_FIELDS nor EXACT_NUMERIC_FIELDS used to fall through to bare == comparison — indistinguishable from a deliberately exact field, and wrong for money. _field_kind now raises UnregisteredNumericFieldError immediately the first time this happens, naming the field — a new derived money field (exactly what a new op like derive_price_per_foot produces) cannot silently score wrong just because someone forgot to register its name. A second, independent net catches it even earlier: a static test walks every gold fixture's numeric values and fails by name if any aren't registered, before replay-gold is even run.

GOLD_ASSERTION_COVERAGE (62 check names classified) is the same discipline applied to the free-text assertions[] array every gold file also carries — a shipped test asserts its key set equals every check name that actually appears across the corpus, so a new gold file introducing an unclassified assertion fails CI immediately rather than being silently ignored.

docs/corpus/validate_gold.py is a separate, narrower check: no pipeline call at all, just "does this gold file agree with itself" — do the line items sum to the subtotal, does prior + current close to the printed total, is amount_payable ever accidentally placed under fields instead of derived. Catches a contradiction in the labels before it ever reaches a real eval run.

The eval commands, and why there are four of them

A single number ("73% of assertions pass") cannot say which stage broke. Each command isolates one slice of the pipeline on purpose:

replay-gold

The whole pipeline, end to end. The number that matters most — "did this change break anything," full stop.

accuracy-report

The exact same numbers as replay-gold, rendered for the non-engineering side of a rollout: percent correct by company and document type, every failure named. A rendering, not a second scoring path.

eval-gate

Classification alone (stages 1–3): doc_type, tags, text source, disposition — before extraction even starts. Isolates a classification regression from an extraction one.

eval-vision

Gemini alone, forced on every document regardless of whether it would really collapse to vision — the fallback's own accuracy, measured directly rather than only on whichever documents happened to escalate.

eval-compare / eval-history

Two recorded runs (by id or by label — a git SHA, "ci", anything) diffed for regressions, or the trend across many runs over time. A candidate may freely gain passes; only a named assertion getting worse counts as a regression.

All four (plus replay-gold) can persist a run via --record-history into var/eval_history.sqlite3, which is what eval-compare/eval-history read from — the same store, four different views onto it.
