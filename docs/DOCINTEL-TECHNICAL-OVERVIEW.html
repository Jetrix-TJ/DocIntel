Overview

The two ideas that explain everything else

docintel is a library other programs embed. It turns one document — a PDF, an email with attachments, an Office file — into a clean, confidence-scored record. Everything below is a variation on two ideas:

Idea 1 — a pipeline you don't assemble. Every document flows through the same eleven stages. build_pipeline() wires all of them — every pack's classification rules, every persona, every hook — from one call. You never hand-build the sequence.

Idea 2 — confidence you don't compute yourself. A band of scoring and routing runs underneath every document, whether or not you opt into anything. You don't decide when a human should look — the pipeline decides, from real signal, and tells you.

The one rule to remember

"Total Amount Due" is a label, not a promise. The naive read-the-biggest-bold-number approach is correct on most invoices and wrong by five figures on the ones that matter — a prior balance already folded in, a credit not yet applied, a scan-line total that encodes the trap value rather than the true one. amount_payable is derived, never copied from the loudest number on the page, and when the arithmetic doesn't close, the record says so and routes to review — it never guesses.

Install & first run

As a library

pip install "docintel[ui] @ git+https://github.com/Jetrix-TJ/DocIntel.git"
from docintel import build_pipeline
from docintel.adapters.vision.fake import FakeVision  # or a real vision adapter

pipeline = build_pipeline(vision=FakeVision())
record = pipeline.process(document_id="d1", source_path="invoice.pdf")

As a CLI

docintel process invoice.pdf --json
docintel serve   # local web UI - upload a document, work the review queue
Does it need any external services to run?

No — the base install runs entirely on rule-based extraction, no API keys, no network calls. [vision] (Gemini) and [generation] (Claude, for onboarding drafts) are opt-in extras; omit them and those code paths simply aren't reachable.

What does --vision fake vs cassette vs live mean?

fake returns nothing (wiring checks); cassette replays recorded responses (offline, deterministic — the default); live actually calls the model. Every documented example in this page runs fully offline unless stated otherwise.

Part 1 · The pipeline

One document, end to end

Follow a single document from .process() to a delivered record. Each numbered step names the stage and the guarantee that fires there. The green ring is terminal — a record is always emitted, whatever happened upstream.

A document arrives — a plain call, no queue required
pipeline.process(document_id, source_path). There's no daemon, no watcher inside docintel itself — your own inbox rule, webhook receiver, or upload handler decides when this fires.
Intake & filter
A PDF is read directly; an .eml/.msg is unwrapped into one IntakeItem per real attachment; .docx/.xlsx is converted to PDF first. Non-document attachments are filtered before anything expensive runs.
Classify — which company, which document type
Claim rules (markers + vetoes) decide whose document this is; a per-company doc_type ladder — a list of signal-based rungs, first match wins — decides what kind it is.
Persona lookup
(sender_fingerprint, doc_type) resolves to a persona — hit (a real persona), or hard_miss (nothing configured yet, escalates rather than guessing).
The extraction cascade: 5a → 5b → 5c
Cached rules (5a, zero AI calls) run first. A field a persona flags with field_hints can fall back to Gemini vision (5b) — never for structure it wasn't asked about. A hard miss escalates to a real, persistent review-queue job (5c) — never a silent drop.
Capture fields
Adjust ops run — alias resolution, sign normalization, derived-value computation (amount_payable and friends) — all from a closed, tested op registry.
Confidence gate
Decides lane (high/medium/review/low), review_flag, regen_flag. Any registered beforeEmit hook fires right after this, seeing the real decision.
Emit — always exactly one record
Even a document that dead-letters mid-pipeline still produces a valid, contract-checked record. count(intaken) == count(emitted) is a machine-checked invariant, not a convention.
Why this order matters

Classification and persona lookup happen before any AI call — a company with no configuration yet is caught cheaply, at Stage 4, not after an expensive vision round-trip. The confidence gate runs after extraction finishes, so a real-time notification hook always sees the finished routing decision, never a partial one.

Part 2 · Deep dives

01Classification & claim rules

How it works

A pack claims a document via markers (printed names/emails/addresses in a scoped block of the page) and can veto a claim (e.g. its own address appearing only in a "ship to" block, not as the actual bill-to). Once claimed, a doc_type ladder — an ordered list of rungs, each a signal-based condition, first match wins, falling through to a default — decides what kind of document it is. Both are declarative: JSON for a data-only pack, no Python required.

Can two companies both claim the same document?

Packs are tried in a fixed, deliberate order and the first to claim wins — order matters precisely because ambiguous claims are possible on real mail (a freight company's own address routinely appears on documents billed to somebody else).

What happens when nothing claims it?

It's no_persona — not misfiled as a hard miss on some default company. The web UI names it plainly and points at the onboarding template rather than a dead end.

Can I add a new doc_type without touching Python?

Yes, for a data-only pack — the ladder, tags, and claim rules are all declared in pack.json. A closed, tested signal registry (12 signals) is what a rung's condition is built from; nothing invents a new detector inline.

02The extraction cascade

How it works

Stage 5a applies a persona's saved selectors — region, anchor, pattern, a closed set of adjust ops — with zero AI calls; this is the high-volume path for every document a company has already been onboarded for. Stage 5b calls Gemini vision, but only for fields a persona's own field_hints name — it is never given free rein to decide what the document contains or how it should classify. Stage 5c escalates a genuine hard miss (no persona at all) into a real, persistent job a human resolves — never a silent drop into "extracted nothing."

Does vision ever get to invent document structure?

No — it answers specific field questions a persona already poses. Classification, routing, and lane decisions are made entirely outside the vision call; sanitizing whatever it returns is a dedicated policy boundary (adapters/vision/policy.py), not a trust assumption.

What if Gemini returns something malformed or off-topic?

sanitize() is the one place every vision result is checked before it can touch a record — an untyped, external response never reaches ctx.extracted raw.

Is there a real cost/latency tradeoff between 5a and 5b?

Yes, by design: 5a is free and instant once a persona exists; 5b costs a real API call and only runs for the specific fields a persona flags as needing it — not as a blanket fallback for anything 5a missed.

03Confidence & the review queue

How it works

Every field gets a confidence score; per-field thresholds (declared per pack) decide whether a document lands in high (auto-approved), medium, review, or low. A status: draft persona applies an automatic 0.85 confidence penalty and can never reach high — a new persona is provably reviewed before it's trusted with auto-approval, not just documented as reviewed.

What actually decides high vs. review?

Per-field thresholds set in the pack, evaluated at Stage 7 (the confidence gate), plus a handful of hard rules — a hard miss, a collapsed persona, an unresolved arithmetic mismatch — that force review_flag=True regardless of the numeric score.

Does a reviewer's correction ever improve future runs on its own?

Not automatically, and deliberately: promote-correction is a separate, human-run command that turns an accepted correction into a new gold-corpus fixture. Nothing silently retrains or auto-promotes a persona from review-queue activity.

What if nobody's watching the queue?

docintel queue-status --fail-if-older-than-hours N exits non-zero past a threshold — built to be polled from cron, the honest minimum for a tool with no dedicated on-call process. See §04 for getting notified without polling at all.

04Real-time notification

How it works

docintel ships no inbox watcher or webhook receiver of its own — that's your infrastructure, whatever it looks like. What it does ship is a hook seam: build_pipeline(hooks=...) accepts a caller-built HookRegistry, and a beforeEmit hook fires the instant lane/review_flag/regen_flag are decided — for every document, inline, in the same call that processed it.

from docintel import build_pipeline, HookRegistry

def notify_if_needs_review(ctx, nxt):
    ctx = nxt(ctx)  # let the pipeline finish deciding lane/review_flag first
    if ctx.review_flag or ctx.lane == "low":
        my_own_notifier(ctx.document_id, ctx.lane)  # your Slack/email/webhook
    return ctx

hooks = HookRegistry()
hooks.register("beforeEmit", notify_if_needs_review, pack="my_integration")
pipeline = build_pipeline(vision=FakeVision(), hooks=hooks)
Does docintel push to Slack/email/a webhook for me?

No, by design — the channel is your own code, in the hook body. docintel doesn't hold credentials or guess your infrastructure; it makes the extension point a one-line registration instead of a hidden internal detail.

What if my hook throws?

Wrapped as a PackError, the same treatment any pack hook gets — the document dead-letters rather than crashing the run, and the exception names your hook and pack.

Can I call .process() from multiple threads for throughput?

Not on the same Runner — it keeps small per-run mutable state (an in-run duplicate index, counters) that isn't thread-safe. Build one Runner per worker instead; build_pipeline() is cheap to call again since packs/personas are cached process-wide.

05Onboarding a new company

How it works

Three commands, in order: generate-persona calls Claude once against one sample document to draft a field list — name, type, one-sentence hint — from a closed vocabulary, never selector geometry. new-pack scaffolds a pack.json and a starter persona from that draft, every region/anchor left an explicit placeholder. validate-persona self-checks the result against the same 14 rules the real pipeline enforces, before anyone else looks at it.

Does generation ever guess the selector geometry?

No, deliberately. An internal test had a blind agent write full selectors from one PDF and score 194/283 against the shipped personas' 238/283 — losses almost entirely in geometry. A follow-up found deleting every anchor/region from the vision prompt moved 1 value in 102. The field list and hints generalize; the coordinates don't, so they stay a human's job.

What happens to a bad draft?

Nothing — it's a JSON file on disk, labelled "status": "draft - not reviewed", never registered anywhere. Nothing on the real pipeline's path reads it until a human wires it into registry.PACK_FILES.

How fast can I actually add a new vendor?

Minutes to a scaffold and a self-check; the real work is still authoring correct selector geometry against a real sample and confirming extracted values by eye — this tooling removes the blank-page problem, not the review.

06Growing the accuracy corpus

How it works

replay-gold scores the whole pipeline against a hand-labelled corpus; accuracy-report renders the identical numbers as a plain-language summary — percent correct by company and document type, every failure named — for someone who isn't reading code. draft-gold turns one clean pipeline run directly into a new gold-fixture draft, with no review-queue correction required first.

Does draft-gold auto-approve its own routing decision?

Never — expected_routing (review_flag/regen_flag/lane) is always left an explicit placeholder, even though the full pipeline already ran and that decision is sitting right there. A gold fixture exists to check routing independently; copying the pipeline's own answer back at itself would make the check permanently, trivially true.

How is "percent correct" actually computed?

accuracy-report is a pure rendering of replay-gold's own assertion counts — same scoring function, same corpus, grouped differently. It is never a second, separately-tuned metric.

07Multi-format intake

How it works

A directory of mixed files is walked once; each PDF is read directly, each .eml/.msg unwraps into one IntakeItem per real attachment (never the email container itself, and never double-counting a directory's own PDFs), and each .docx/.xlsx is converted to PDF first via headless LibreOffice.

An attachment inside an attachment (a forwarded email as a file)?

Each container is unwrapped one level; a nested email-as-attachment is treated as an opaque attached file at that level, not recursively re-opened as its own container today.

What happens on an unsupported format?

A per-document, per-format decision at the intake boundary (extract.convert.ACCEPTED_SUFFIXES) — an unsupported file is skipped with a named reason, never silently attempted and quietly failing deep in the pipeline.

Part 3 · Straight talk

Honest limitations & deliberate deferrals

What a reviewer should know is intentionally not addressed today, so nothing reads as an accidental gap:

AreaStatus todayWhy
Concurrency across a shared RunnerNot thread-safe to share; one Runner per worker is the supported patternAn in-run duplicate index and counters are plain mutable state, deliberately scoped to a single sequential run.
Inbox/webhook watcherNot shipped, by designWatching a live mailbox is the caller's own infrastructure; the hook seam (§04) is the extension point, not a built-in poller.

Part 4 · Next phase

08What's proposed, not shipped proposed — not shipped

Where docintel stops today

The hook seam (§04) gets a caller notified the instant a document needs attention. It stops there: docintel doesn't ship a reference implementation of what to do with that notification, and it doesn't yet generate real selector geometry for a brand-new vendor. This section names what a next phase would close, written the same way Part 2 documents what already exists, so it's evaluated as a plan rather than mistaken for a shipped feature.

Reference notifier

A small, optional package built on the existing beforeEmit hook — a real Slack/email/webhook sender a team can adopt directly instead of writing the callback body from scratch.

Real selector-geometry generation

Anamul's original standup ask, in full — genuinely harder than the field-hint draft this session shipped, and by JA's own words "still 100% not ready." Needs real progress on the geometry-generalization problem §05 documents, not just a bigger prompt.

Concurrent-safe Runner

A thread-safe variant (or a documented pooling pattern) for services that want one long-lived pipeline object rather than one per worker.
