What doesn't exist yet — the layers between "review" and "paid"

The review queue this session built solves "a human needs to look at this" — it does not solve what happens after. Every production AP platform has these; this system currently has none of them:

Approval workflow

Once a reviewer resolves a job, nothing routes the underlying invoice to an approver, tracks approval status, or blocks payment until approved.

Payment scheduling

No integration point to an AP/ERP system to actually schedule the payment once a record is auto-approved or manually cleared.

Audit trail / SoD

Who resolved what, when, and whether the same person who flagged an exception can also clear it — not modeled at all today.

Multi-worker scaling

PackPersonaStore is parsed once per process; a real deployment needs shared, persistent persona/job storage the moment there's more than one worker (already noted in the production plan).

Cost/concurrency cap on vision calls

No budget guard before the vision fallback path sees real production volume.

Contract↔invoice matching

The subject of the rest of this document — the one substantive extraction/reconciliation capability that's missing, not just an ops-maturity gap.

Why contract↔invoice matching is the next real feature

This isn't a hypothetical priority — it's already in this repo's own feature plan (docs/BUGS-FEATURES-PRODUCTION.md, items 5–6), triggered by a real finding: of 18 real documents that processed cleanly in the corpus sample, 16 were contracts, amendments, or Customer Service Records — none of them bills — matched to a carrier's billing persona purely because the carrier's name appears on the page, then run through billing-shaped extraction that has nothing to reconcile against. The document type doesn't exist in the domain model yet.

This is a known, well-understood industry problem — not a novel one Telecom expense audits are specifically defined as checking billed rates against contracted rates, line by line, and industry data puts the error rate at 7–12% of enterprise telecom invoices — a $50/month rate mismatch on one circuit is nothing, but across 200 circuits that's $120,000/year in exposure from rate errors alone.3 This is exactly the domain the shipped packs already operate in (telecom, recycling/waste AP) — so this feature isn't a detour, it's completing the loop the corpus is already pointing at.

The broader industry pattern this maps onto is N-way invoice matching: 2-way (PO vs. invoice) for service contracts with no physical delivery, 3-way (PO + invoice + goods receipt) where something is physically received.4 This system has no purchase-order concept — its analogue is invoice ↔ contract, the 2-way case, which is exactly right for telecom/recycling service billing where nothing is "received," only billed.

Architecture — reusing what already exists, not inventing a parallel system

The design constraint from the existing feature plan is explicit: a downstream consumer, not inside the fast lane. That's correct, and it matches how every production system actually does this — matching runs after both documents are individually extracted, never woven into single-document extraction.5

What's genuinely new

  • A contract doc_type — one new classification signal, one new field set (account/circuit ID, rate table, term start/end, signatory). Reuses the identical selector-grammar mechanism bills already use; zero new extraction machinery.
  • A contract store — same shape as PackPersonaStore, but keyed by (pack, account_or_circuit_id) → a list of contract records, not one. This is the load-bearing design decision: the existing "latest wins" instinct is already known-wrong (the Golub Corporation relationship in this repo's own test data has a 24-month contract, a 36-month contract, and several amendments layered on top — see the open item already logged in docs/BUGS-FEATURES-PRODUCTION.md).
  • A reconciliation stage — takes an already-emitted invoice record plus whatever the contract store returns for its match key, applies a tolerance band (see below), and either finds a clean match or raises exactly one of the four flags in the diagram.

What's reused, unchanged

  • The alias/canonicalization mechanism (aliases.py) resolves "Circuit# 12345" and "CKT-12345" to the same key — no new matching logic needed, same as vendor-name canonicalization today.
  • The job queue and /review UI this session built — one new kind="contract_reconciliation", same schema, same routes, same overlay-vs-audited-table precedence pattern (a reviewer's manual match confirmation is the lower trust tier; a corrected contract record is the audited one).
  • The fields/derived separation — reconciliation output is additive (a new record["reconciliation"] block), never a rewrite of derived.amount_payable. The existing derivation logic (F1) answers "what do we owe on this invoice alone"; reconciliation answers a separate question ("does that number agree with what was contracted") and must not blend the two, for the same reason fields and derived are already kept apart.

The tolerance band — borrowed directly from industry practice

Real AP teams don't flag every cent of variance — that would make the exception queue unusable. The industry-standard default is ±2% price variance, tightened for new/unproven vendors and loosened for trusted recurring ones, set per vendor rather than globally.6 This maps directly onto this codebase's existing per-pack thresholds mechanism (already used for confidence, already pack-scoped) — the same config surface, one more key.

// packs/<pack>/pack.json or conventions.py — same pattern as existing thresholds
"reconciliation_tolerance": {
  "rate_variance_pct": 2.0,      // industry default; tighten for new vendors
  "new_vendor_rate_variance_pct": 0.5
}

Real-world research digest

What production AP-automation platforms actually do today, and how it maps onto this system.

Matching discipline

3-way matching (PO + invoice + goods receipt) is the standard for physical goods; 2-way (PO/contract + invoice) is standard for service invoices with no delivery event4 — exactly this system's situation. Fraud protection is a real, cited driver: 79% of organizations experienced payment fraud in 2024, average loss over $130,000/incident8 — a fraudulent invoice can't produce a matching contract for services never agreed to, which 2-way matching directly defeats.

Exception handling is shifting from "queue" to "agent-assisted queue"

Current-generation platforms deploy specialist agents that investigate a mismatch (check the contract, review historical invoice patterns for that vendor) and either resolve it automatically or route it with a recommended resolution — the human's role shifts from investigating to reviewing what the agent already resolved.9 This system's job queue is the right foundation for that evolution later, but should ship first as a plain queue — resolving automatically before the reconciliation logic itself is proven would repeat this project's own established mistake pattern (guessing instead of refusing).

Confidence-based routing is now table stakes, not a differentiator

By 2026, top IDP platforms all advertise 90–99% accuracy on common formats — the differentiation has moved to exception handling and routing, not raw extraction.10 Fields below a ~90% confidence threshold route to human review by convention across platforms11 — this system's DEFAULT_THRESHOLD = 0.90 in s7_gate.py already matches that convention exactly, unprompted.

Ingestion architecture

Production document pipelines are multi-stage and queue-based: an intake layer (API upload, email parser, SFTP, cloud storage) feeds a background task queue so uploads are never blocked on processing, with the same ingestion path used regardless of source channel.12 This maps onto item 8 in this repo's own feature plan (real-time, multi-document upload) — the architecture described there (object storage → jobs table → worker pools) is exactly the pattern production systems use, not a novel proposal.

Contract lifecycle risk

Continuing to bill or be billed after a contract's expiration carries real legal exposure, not just a bookkeeping inconvenience7 — reinforcing that billed_after_contract_expiry deserves the same forced-review treatment as arith_balance_mismatch already gets, not a soft warning.

Recommended phase plan

  • Near term — close the STP gap on what already exists

    Bugs 1–3 from the existing bug list (vision-escalation coverage check, label-block overcapture, table-break detector) are the fastest lever on the 55.9%→70%+ target, since they're silent-wrong-data risks, not missing features.

  • Near term — ship the contract doc_type alone, no reconciliation yet

    Just classification + extraction into the new field set. This alone fixes the 16-of-18 misclassification finding and is independently valuable (a contract repository) before reconciliation logic depends on it.

  • Mid term — reconciliation, cases 1–6 from the test matrix

    The straightforward cases: exact/tolerance match, outside-tolerance, no-contract-found (both flavors), expired. Ships real value fast, reuses the existing job queue entirely.

  • Mid term — reconciliation, cases 7–13

    Date-aware amendment resolution and the multi-contract-ambiguous refusal are the ones that need the real Golub-style test data this repo already has — build against real cases, not synthetic ones, matching this project's own established evidence discipline.

  • Long term — the layers between review and paid

    Approval workflow, payment scheduling integration, audit trail, multi-worker persistent storage — needed before this is a system of record, not before it's a useful extraction tool.
