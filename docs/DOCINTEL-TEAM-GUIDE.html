Document Intelligence · Getting started

Install it, run one document, onboard your first vendor

This is the practical path, in order: get the library running, process a real document, then teach it a vendor your team cares about — without ever touching the installed package's own source. Everything here was run for real while writing it; nothing is theoretical.

1

Install

A fresh, isolated environment — this never touches anything else on the machine:

python -m venv venv
.\venv\Scripts\Activate.ps1
pip install "git+https://github.com/jeevatechjays/DocIntel.git@classification-correctness-v2"

Confirm it's a real, installed package (not pointing at some other checkout):

python -c "import docintel; print(docintel.__file__)"
pip show docintel
Branch note Drop @classification-correctness-v2 once this branch merges to main — the same command then installs the default branch.
2

Process a document

docintel process "C:\path\to\some-invoice.pdf" --vision fake --json

--vision fake is correct for any document with no pre-recorded test cassette — which is every real document you didn't build a fixture for. It skips the vision fallback and shows exactly what the deterministic rules capture on their own.

Read the result by checking three things first:

KeyWhat it tells you
dispositionprocessed is normal. dead_letter means something broke — read reason.
extraction_coveragecomplete: true means every declared field for this doc_type was found.
lane / review_flagreview or flag: true isn't a bug — it means the pipeline isn't confident enough to auto-approve. A brand-new "status": "draft" persona always does this, on purpose.

An unrecognized vendor comes back tagged no_persona/unclaimed_document, not guessed at — that's the safe path working, not a gap to panic about.

3

Onboard a new vendor

Two different situations, two different mechanisms — both live entirely in your own project folder, never inside the installed package, so pip install --upgrade can never wipe them out.

A vendor for a company docintel already knowssimplest

Adding another AP vendor to northstar (or another vendor to spt_metals/acme_freight). One environment variable, zero scripts:

my_docintel_config\ northstar\ aliases.local.json {"widget vendor llc": "widget_vendor"} widget_vendor.json (a persona)
$env:DOCINTEL_EXTRA_PERSONAS_DIR = "C:\path\to\my_docintel_config"
docintel process "widget-vendor-invoice.pdf" --vision fake --json

The CLI picks this up automatically through the env var — nothing else to wire.

Tested — one real exception: digitaldirection Confirmed by an actual run: this works cleanly for northstar because it claims by its own fixed bill-to identity — the vendor's name never enters the claim decision. digitaldirection claims by carrier instead, via an alias_table rule compiled once from the shipped, hardcoded alias table — the overlay's aliases.local.json never reaches it. A brand-new carrier added only through the overlay comes back unclaimed_document unless it happens to bill an existing managed client (the secondary roster rule), or its name is added to the real LITERAL_ALIASES table — a genuine code change, the same one Spectrum needed this session. Check a pack's claim rule kind before assuming the overlay alone is enough for it.

A whole new company — nothing claims it yet

Project layout:

my_project\ venv\ ← untouched install invoices\ ← your real PDFs my_packs\ <company_slug>\ pack.json personas\ <vendor_slug>.json run_pipeline.py

pack.json — the claim rule, doc types, field set, and a one-rung ladder (real, working example):

{
  "name": "acme_widgets",
  "default_currency": "USD",
  "doc_types": ["invoice"],
  "thresholds": { "total_printed": 0.90, "invoice_number": 0.90, "bill_to_name": 0.90 },
  "fields": {
    "invoice": {
      "all": ["vendor_name", "bill_to_name", "invoice_number", "total_printed"],
      "required": ["bill_to_name"],
      "any_of": [["invoice_number"]],
      "derived_only": []
    }
  },
  "claim": {
    "rules": [{ "kind": "markers", "scope": "primary", "values": ["ACME WIDGETS"] }],
    "vetoes": []
  },
  "ladder": {
    "default": "invoice",
    "rungs": [{
      "name": "invoice_confirmed", "doc_type": "invoice",
      "when": { "signal": "pattern_in_scope",
                "params": { "pattern": "ACME WIDGETS", "scope": "primary" } }
    }]
  }
}

personas/<vendor_slug>.json — where each field sits on the page (full region/pattern vocabulary: reference):

{
  "rule_version": "v1",
  "status": "draft",
  "doc_type": "invoice",
  "sender_fingerprint": "acme_widgets|acme_widgets",
  "field_selectors": [
    { "field": "vendor_name", "region": "top-left", "pattern": "text" },
    { "field": "bill_to_name", "anchor": "BILL TO", "region": "near-anchor", "pattern": "text" },
    { "field": "invoice_number", "anchor": "INVOICE NO.", "region": "near-anchor", "pattern": "text" },
    { "field": "total_printed", "anchor": "TOTAL", "region": "near-anchor", "pattern": "currency" }
  ]
}

Validate before running it for real:

docintel validate-persona my_packs\acme_widgets\personas\acme.json --pack-file my_packs\acme_widgets\pack.json

run_pipeline.py — ties it together via extra_packs=, scans the whole invoices\ folder:

import json, os
from collections import Counter
from docintel import build_pipeline
from docintel.adapters.vision.fake import FakeVision
from docintel.adapters.intake.filesystem import FilesystemIntake
from docintel.packs.datapack import load_pack_file

HERE = os.path.dirname(os.path.abspath(__file__))
pack = load_pack_file(os.path.join(HERE, "my_packs", "acme_widgets", "pack.json"))
pipeline = build_pipeline(vision=FakeVision(), extra_packs=[pack])

dispositions = Counter(); records = []
for item in FilesystemIntake([os.path.join(HERE, "invoices")]).items():
    record = pipeline.process(document_id=item.document_id, source_path=item.source_path,
                               sender_email=item.sender_email, email_id=item.email_id)
    dispositions[record["disposition"]] += 1
    records.append(record)
    print(f"{record['disposition']:<12} {record['lane'] or '-':<7} "
          f"{record['doc_type'] or '-':<15} {item.source_path}")

json.dump(records, open(os.path.join(HERE, "results.json"), "w"), indent=2)
print(f"\n{len(records)} processed ({', '.join(f'{n} {d}' for d, n in dispositions.items())})")
Proven, not just described Built and run this exact way against three real invoices from three different clients: 24/24 field values correct against hand-checked ground truth, correct claim, correct persona lookup, zero repo edits, zero dead letters.
4

Verify at scale

Drop more PDFs into invoices\ (subfolders are fine) and rerun the same script:

.\venv\Scripts\python.exe run_pipeline.py

The terminal prints one line per document; results.json next to the script gets full field-level detail for every one. If a new document comes back with missing_required fields or lands in review/no_persona, that's real signal — either a selector needs adjusting for a slightly different layout, or it's genuinely a different vendor that needs its own persona.

5

Gold data & automated scoring

Checking output by eye doesn't scale past a handful of documents. Gold data is a hand-confirmed JSON file per document holding the correct answer — the same mechanism this project's own test suite uses, reusable from your own project with zero code changes, since the gold folder and PDF lookup are both plain relative paths: 

from docintel.scorecard import replay_gold
from docintel import build_pipeline
from docintel.adapters.vision.fake import FakeVision
from docintel.packs.datapack import load_pack_file

pack = load_pack_file("my_packs/acme_widgets/pack.json")
card = replay_gold(runner_factory=lambda: build_pipeline(vision=FakeVision(), extra_packs=[pack]))
print(card["summary"])   # {'total': N, 'passed': N, 'failed': 0, ...}

Two ways to write the gold file itself:

  1. Hand-write it — a JSON file under docs\corpus\gold\, naming the source PDF and every expected field value.
  2. Auto-draft it from one clean run, then just review it — much less typing: 
    from docintel.evals.draft_gold import draft_gold_fixture
fixture = draft_gold_fixture(record, "acme-widgets-inv-0001", source_file="invoice.pdf")
    This fills in fields/derived/line items straight from the record. It never auto-fills expected_routing (lane/review_flag) — that's the one thing gold data exists to check independently, so a human sets it by hand after looking at the record.

Rerun replay_gold after any persona change — it's the "did I just break something" check.

6

Troubleshooting — real gotchas we actually hit

A field grabbed the wrong text

region: "near-anchor" is a wide box (300pt right, 40pt below the anchor) — a label sitting at the same height in a neighbouring column can leak into it. The "text" pattern makes this worse: it accepts whatever candidate it sees first, even if that's the wrong column.

Fix Use a targeted regex instead of the generic "text"/"date" shortcuts. For a party name, an anchored Title Case shape (^([A-Z][a-z]{1,15}\.?(?: [A-Z][a-z]{1,15}\.?)?...)$) rejects an all-caps label like INVOICE NO. outright, letting the pattern loop fall through to the real value on the next line down.

A date field came back empty

The named "date" pattern only parses month-first strings (Aug 19, 2026). A day-first date (19 Aug 2026) silently fails to parse — the field is simply missing, not wrong.

Fix Use a plain regex instead: ([0-9]{1,2}\s{1,3}[A-Za-z]{3,9}\s{1,3}[0-9]{4}) — records the raw printed text rather than trying (and failing) to normalize it.

A persona won't validate

Two rules on regex patterns, enforced by docintel validate-persona:

  • No unbounded quantifiers — \s+ fails, use \s{1,3}.
  • No quantified group containing another quantifier — (?:X{1,15}){1,4} fails; write out repetition as separate optional groups instead ((?:X{1,15})?(?:X{1,15})?).

Everything lands in review lane

Normal for a brand-new persona: "status": "draft" applies an automatic confidence penalty on every document. Promote to "active" once you've checked real coverage across enough samples.
