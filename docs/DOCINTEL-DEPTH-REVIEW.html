Why docintel is built the way it is, and how well that's holding up

Executive summary

A rules engine with a narrow, supervised escape hatch

docintel turns a vendor invoice into a structured, confidence-scored record. The core bet is that classification and extraction should be data, not code — a closed, validated grammar a non-engineer can review, with AI used only as a fallback for the specific values a rule-based read couldn't get, never for deciding what a document is. That bet has now been tested by two people neither of us directed, on real invoices, and it holds up — with two real bugs found and fixed-worthy, and one genuinely open limitation worth your attention below.

Bottom line
Production-viable for a configured vendor. Two confirmed bugs on the unconfigured/vision-only path need fixing before that path is trusted the same way.

Design philosophy

Two ideas that explain everything downstream

Idea 1 — a document's identity is decided by rules a human can read, never by a model's judgment. Every classification decision (which company, what document type) is compiled from a pack's pack.json — a closed set of rule kinds and signal names, validated at load time. There is no code path where an LLM decides "this is an invoice from Acme." That is a deliberate, load-bearing constraint, not a missing feature: a rules engine is auditable and reproducible in a way a model's classification never fully is, and for an AP workflow, reproducibility is the product.

Idea 2 — a value the page doesn't answer directly gets derived, never guessed. "Total Amount Due" is the headline number on an invoice; it is routinely not what's actually owed once a prior balance or a credit is folded in. The pipeline's own worked example is a real document where trusting the printed total overpays by $20,123.80. Every derived value either closes its own arithmetic or explicitly refuses and routes to a human — it never averages, never estimates, never picks the more plausible of two numbers.

closed grammar

A persona can only reference a fixed vocabulary of regions, patterns, and ops — never arbitrary code. This is the actual security boundary: "there is no sandbox because there is nothing to sandbox."

fail-loud validation

14 numbered rules reject a malformed persona write outright, all-or-nothing — never a partial, half-migrated rule set.

emit-always

Every document produces exactly one record, success or failure. count(intaken) == count(emitted) is a machine-checked invariant, not a convention.

The pipeline, and why 11 stages instead of 3

The stage count looks like a lot for "read a PDF, get some fields." It's split this finely because each boundary is where a specific, previously-real failure mode gets caught. The branching below is the part prose alone tends to flatten — three separate escalation exits, each reachable only when the stage before it genuinely failed, never as a default path:

Classification as data — and its one real asymmetry

A pack claims a document via a small, closed set of rule kinds (markers, corroborated_markers, alias_table, roster_on_short_line), then an ordered ladder of signal-based rungs decides the specific document type. Both are plain JSON, validated at load time, extending the exact discipline the project's own selector grammar already established for extraction.

A real, confirmed asymmetry between claim rule kinds

markers-kind packs (northstar) claim on their own fixed identity (the bill-to), so adding a new vendor never touches the claim decision at all — verified live this session. alias_table-kind packs (digitaldirection) claim on the sender's name, read from a table compiled once at import — so a genuinely new carrier added only through the external-onboarding overlay is never claimed at all, even with a perfectly correct persona sitting there, unless it happens to bill an already-known client. This is not a bug so much as an incomplete extension point: the override reaches persona lookup and fingerprinting but not this one claim path.

Extraction as a closed grammar, not a prompt

A persona's field_selectors describe where a value sits (an anchor + a region) and what shape it has (a named pattern or a restricted regex) — never "read the total." The restriction is deliberate: a raw regex is capped at 200 characters, one capture group, a 50ms budget, no backreferences, no unbounded quantifiers — a linear-time guarantee that makes the timeout budget honest rather than theoretical.

14 validation rules (V1–V14) reject a bad write before it ever reaches a real document. The most important of them, V10, makes it structurally impossible for a selector to target amount_payable directly — closing off the single easiest way to reintroduce the $20,123.80-class bug, because on 7 of the original 10 corpus documents such a selector would look perfectly correct.

Derivation: the discipline that makes "confident" mean something

Confidence in this system is not a vibe — it's a multiplicative product of named, enumerable modifiers (16 of them), each with a specific, documented trigger. A field can only ever end up less confident for a stated reason on the record; the one exception — a cross-check agreeing — is capped at a 1.10 multiplier and can never push a field above 0.99, because agreement between checks is corroboration, not proof.

The one rule worth internalizing

derive_amount_payable never guesses. If the arithmetic doesn't close within a cent, it sets the value to null, applies a mismatch modifier, and forces a review flag — regardless of how confident every individual field looked. This is the difference between a system that's honest about uncertainty and one that just hides it.

The AI boundary — where it's allowed to help, and where it never is

Gemini is called only in Stage 5b, and only after cached rules have already run and "collapsed" — no match quality at all, two or more fields scoring below 0.50, or most of what a persona declared came back empty. By the time that could even happen, classification and persona lookup are already finished. The model never sees "which company is this" as a question — only "what does this specific field say."

A persona-less, fully-unclaimed document still gets one shot at vision — but only for four default fields (vendor_name, invoice_number, invoice_date, total_printed), never the richer field set a real persona would define. This is the honest tradeoff of the "no persona yet" path: some data beats none, but it is structurally less than what a configured vendor gets.

A real gap this session's independent testing surfaced, not yet fixed

The escalation stage's own guarantee — "a hard miss always gets a review flag, so a human sees it" — is silently conditional: if every field's self-reported vision confidence is ≥0.60 (which a model with no calibrated uncertainty essentially always reports), the review flag is never set and no job is queued. A brand-new, entirely unconfigured vendor can process with a high lane and zero human visibility. This was found by an independent test run against 20 real invoices, not by us — worth fixing before this guarantee is relied on for a genuinely new sender.

The extension architecture

Why extra_packs= and the personas overlay exist at all

A team that only pip installs this library had no way to add a vendor without either editing installed site-packages (silently wiped by the next upgrade) or monkey-patching module internals this project never promised to keep stable. The fix generalizes a pattern the project already trusted for one specific case — a per-pack, gitignored *.local.json overlay for billing conventions — to personas and aliases broadly, rather than inventing a second mechanism.

Both extension points are now independently validated: this session's own Spectrum/Jeeva Enterprises/Acme Widgets work, plus — separately — another engineer's real onboarding of four new companies for RFQ intake, entirely as pure-data packs, zero Python (see below).

The two extension folders answer different questions

my_packs/ answers "no pack claims this at all" — you supply the whole Pack object. DOCINTEL_EXTRA_PERSONAS_DIR answers "a pack already claims this, it just doesn't know this specific vendor yet" — you supply only the missing persona and alias entry. Reaching for the wrong one is the most common early mistake: a brand-new company needs the former; a new customer of an existing carrier needs the latter — and, per the asymmetry above, only if that pack claims by fixed identity rather than by alias_table.

Real-world evidence, not just this session's own testing

The Eclipse Invoice Scorecard — a stress test that found real bugs

An independent run of 20 real AP invoices through the full pipeline, scored with the library's own assertion engine against ground truth it never saw. Verified against source, not taken at face value:

bug matches(kind="money") crashes on the vision route's own raw output (Decimal("$6,500.00") → InvalidOperation) — confirmed, zero currency stripping in that comparison path.
bug The "a hard miss always gets a review flag" guarantee is confidence-gated and silently skipped — confirmed, see the callout above.
gap A scanned document dead-letters on a missing local OCR binary even though the vision route it would otherwise reach sends raw PDF bytes and never needed OCR at all — confirmed ordering problem, not this test's environment.
not a bug "Vendor identity resolved on only 1 of 12" — correctly, 11 of these 12 real-world senders simply have no persona configured yet. The report's own framing gets this right: it's a coverage gap, not a fingerprinting defect.

The RFQ Intake Run — a real onboarding, independently repeated

A second engineer, working from the Feature Explorer guide alone, onboarded four brand-new companies for a completely different document family (RFQs and purchase requisitions, not AP invoices) as pure-data packs. Result: 6/6 documents claimed, 66/66 gold assertions, correct byte-identical duplicate detection. Three of the "gotchas" they hit and fixed were the exact same ones already in this project's own troubleshooting docs — real evidence those docs transfer knowledge, not just describe it. They also surfaced one genuinely new one: an anchor silently never matches when a label and its value are printed with no whitespace between them (Status:Approved), because anchor matching only considers already-tokenized words — confirmed by tracing executor.py::_runs directly.

Maturity verdict

For a properly configured vendor
Solid. Two independent teams, neither of them us, ran real documents through real configurations and got correct, reproducible results — including derivation math, duplicate detection, and gold-corpus regression scoring.
For an unconfigured / vision-only vendor
Not yet trustworthy unattended. The confidence-gated escalation gap means exactly the case this path exists for — a brand-new sender — is the one case where the safety net can silently not catch it.

Recommended next action: fix the two confirmed bugs (money comparison, confidence-gated escalation) before leaning on the vision-only path for any vendor that hasn't been onboarded a persona.
